# 网关排障：从症状到根因的定位纪律

> 本文件面向**自己写的网关**（反代 / LLM 中转 / API 适配层），不是 nginx 配置本身。
> 它解决一个具体困境：**症状出现在 A 层，根因在 B 层，而错误信息指向 C 层。**
>
> 内容全部来自实战踩坑，每条都标注了"当初是怎么被骗的"。

---

## 零、第一原则：先定位层级，再改任何东西

一个请求经过的每一跳都可能出问题：

```
客户端 → [代理] → [网关适配层] → [上游 API] → 上游内部
```

**90% 的误判来自"在错误的层找原因"。** 定位层级的方法只有一个：
**在每一跳的边界上抓真实报文，做逐跳对比。**

### 逐跳抓包矩阵

| 抓什么 | 在哪抓 | 能回答的问题 |
|---|---|---|
| 客户端发的原文 | 网关入站 dump | 客户端到底发了什么 |
| 网关发给上游的原文 | 网关出站 dump | 网关**改写后**发了什么 |
| 上游回的原文 | 出站 dump 的响应侧 | 上游到底报了什么错 |
| 网关回给客户端的原文 | 客户端侧 / 代理 access log | 错误在哪一跳被改写 |

**关键洞察：入站报文 ≠ 出站报文。** 网关会改写请求体（强制字段、清洗指纹、裁剪超限值、归一字段名）。排查"上游报参数错误"时，**必须看改写后的那一份**，看客户端发什么会绕远路。

### 实现 dump 的要点

```go
// 在**唯一的出口函数**上挂钩，不要在各处零散加日志。
// 出口函数通常是签名/构造请求的那一个（所有上游调用都会经过它）。
func (c *Client) signedRequest(...) (*http.Request, error) {
    // ...构造完成...
    if os.Getenv("DEBUG_DUMP") == "1" && isChatPath(rawURL) {
        dumpUpstream(method, rawURL, body, headers)
    }
    return req, nil
}
```

三条纪律：

1. **开关控制**（环境变量），不要默认开 —— 生产环境落盘会撑爆磁盘
2. **脱敏**（`Authorization` / `*token*` 只记长度，不记内容）
3. **同时落盘"最终状态码"** —— 单个文件里既有请求又有结果，才能做因果对应

```go
// 入站侧：返回一个收尾函数，由 defer 在响应结束时回填状态码
dumpDone := dumpRequest(body, r)
defer func() { dumpDone(st.status) }()
```

> **踩过的坑**：只 dump 请求不 dump 结果，面对 200 个文件无法判断哪个对应失败。
> 补了状态码回填之后，"哪个请求失败了"一眼可见。

## 一、HTTP 200 里藏业务错误（最容易被骗的一条）

**症状**：客户端说"请求失败"，但网关日志显示 `status=200`，上游调用看起来全成功。

**真相**：很多上游（尤其国内云 API）把业务错误**包在 HTTP 200 里**返回：

```json
{
  "error_code": "InferHub.4291.200",
  "error_msg": "insufficient quota",
  "details": [{"error_msg": "modelId: glm-5.3-flash"}]
}
```

注意 `error_code` 的**末段才是真实语义状态码**（`.200` / `.404` / `.400`）。

### 由此引发的连锁误判

```
上游返回 200 + "参数非法"
   ↓ 网关只看 HTTP 状态 → 判为"成功"
   ↓ 但流里没有有效数据 → 判为"上游故障"
   ↓ 按故障处理 → 冷却账号 → 换号
   ↓ 只有一个账号 → 轮换耗尽 → 503 "账号不可用"
   ↓ 用户看到"账号不健康"，去查账号
   ↓ 真实原因：客户端发了个上游不认的字段名
```

**一个客户端的坏参数能毒化整个账号池**，并让所有客户端开始 503。

### 修法

```go
// 从 error_code 末段解析真实状态码
func statusFromCode(code string) int {
    i := strings.LastIndex(code, ".")
    if i < 0 || i+1 >= len(code) { return 0 }
    seg := code[i+1:]
    if len(seg) != 3 { return 0 }
    n, err := strconv.Atoi(seg)
    if err != nil || n < 100 || n > 599 { return 0 }
    return n
}

// 分类时用**真实状态码**，不是外层的 200
kind := upstream.Classify(bizStatus, body)   // ✅
kind := upstream.Classify(200, body)         // ❌ 永远落到 ErrNone
```

**并且**：4xx 类错误要**原样回给客户端**，不要报成"服务不可用" ——
"账号不健康"会让调用方以为该重试或换账号，而实际上重试多少次都一样。

## 二、错误分类错误会放大故障

错误分类决定了"罚谁"。分错会雪崩。

| 上游错误 | 正确归属 | 错误归属的后果 |
|---|---|---|
| 参数非法 / 模型名错 | **客户端错误**，不罚账号 | 罚账号 → 好账号被冷却 → 全线 503 |
| 并发上限 | 账号"忙"，**短冷却不熔断** | 喂熔断 → 好账号被误判为故障 |
| 额度耗尽 | 标记该**模型/资源**，不罚账号 | 罚账号 → 换号也没用（换谁都一样） |
| 凭证失效 | 永久禁用该账号 | 反复重试 → 刷屏 + 浪费配额 |
| 网络抖动 | 换号，**不喂熔断** | 累计抖动 → 账号被误熔断 |

### 判定纪律

**宁可漏判也不要误判**。误判的代价是"把可用的东西标成不可用"，
用户会因此避开它；漏判只是多试一次。

```go
// 只在**确认**时标记，其他任何错误都不标记
if reason, ok := DetectQuotaExhausted(body); ok {
    markQuota(model, reason)
}
// 网络错误、并发上限、参数问题 → 一律不标记
```

**成功要清除标记**：额度可能周期性恢复。
只在失败时标记而不在成功时清除，用户会一直看到过期状态。

```go
h.cfg.Pool.NoteSuccess(acct.UID)
h.clearQuota(modelOf(body))   // ← 别漏这行
```

## 三、区分"暂时不可用"与"永久不可用"

同样是拿不到账号，语义完全不同：

| 情形 | 表现 | 正确处理 |
|---|---|---|
| 账号全部冷却/禁用 | 等多久都没用 | 立即 503 |
| 账号健康但**并发满额** | 一会儿就有名额 | **排队等待** |

**把两者混为一谈是常见 bug**：并发满时立即失败，客户端重试又撞上限 → 持续报错。

### 排队实现要点

```go
// 1) 先问清楚是哪种
if !pool.HasCapacitySoon() {   // 全部冷却/禁用
    return 503
}
// 2) 只是忙 → 排队
if !pool.WaitForSlot(ctx, timeout) {
    return 503
}
```

**三条硬要求**：

1. **ctx 取消要立即退出** —— 客户端断开后不能把 goroutine 永久挂住
2. **必须有超时兜底** —— 无限排队会堆到内存耗尽
3. **排队层自身不能超发** —— 上游的限制是硬的，自己超发等于没做

```go
// 用轮询而非条件变量：
// 名额释放在 Release 的任意调用里，要唤醒等待者就得让热路径持锁广播。
// 而排队是"秒级、低 QPS"的，20ms 轮询几乎无感，却让 Release 保持无锁廉价。
const pollInterval = 20 * time.Millisecond
```

### 超时取值

参考上游单次耗时：**超时 ≈ 单次耗时 × 可接受排队数**。
例：单次 1–3 秒、并发 3 → 30 秒足够消化 ~10 个排队请求；再长客户端多半已自行超时。

## 四、上游参数契约：白名单而非黑名单

**不要"原样透传 + 清洗已知脏字段"**，要**"只发上游认识的"**。

理由：上游对未知字段的处理方式不一致 —— 有的忽略，有的**直接 400**。
若会 400，加上第一节的分类 bug，**一个客户端的新字段就能打挂整个网关**。

```go
var supportedFields = map[string]bool{
    "model": true, "messages": true, "stream": true,
    "tools": true, "tool_choice": true, "temperature": true,
    // ...只列上游确实认识的
}

func applyFieldWhitelist(obj map[string]any) {
    for k := range obj {
        if !supportedFields[k] { delete(obj, k) }
    }
}
```

### 顺序很重要

```
先归一（新字段名 → 上游认识的旧名）→ 再裁剪（超限值 → 上限内）→ 最后白名单
```

顺序反了会把刚映射出来的字段也删掉。

### 字段名兼容的典型坑

| 客户端发的（新规范） | 上游只认（旧名） | 不转换的后果 |
|---|---|---|
| `max_completion_tokens` | `max_tokens` | 400 参数非法 |
| `developer` role | `system` role | 400 role 白名单拒绝 |
| `tool_choice` 对象形式 | 字符串 | 400 类型不匹配 |

**并且要裁剪超限值**：客户端会发远超上限的值（实测见过发 384000 而实际上限 65536）。
**裁剪而非报错** —— 客户端要的是"尽量长的输出"，给它上限即可；
因为"要多了"让整个请求失败没有道理。

## 五、定位"谁在请求"（诊断反被诊断误）

排查时经常需要回答"这些请求是谁发的"。

### 命令

```bash
# Windows：谁建立了到本机端口的连接
netstat -ano | findstr ":17863.*ESTABLISHED"
# 排除服务自身 PID 后，剩下的就是客户端

# Linux
ss -tnp | grep ':17863'
```

拿到 PID 后查进程与命令行：

```powershell
Get-Process -Id <PID> | Select-Object ProcessName,Path
Get-CimInstance Win32_Process -Filter "ProcessId=<PID>" | Select-Object CommandLine
```

### ⚠️ 最重要的教训：**先排除你自己的诊断工具**

**实战踩坑**：排查"谁在疯狂请求"查了一轮 AIClient2API、DSH、浏览器，
最后发现是**自己几小时前建的一个后台诊断循环**（`for round := 0; ; round++`，无终止条件），
它制造了上万个请求，还污染了所有后续观察：

- "每秒 12-15 个请求" → 是自己的工具打的
- "并发会话上限" → 自己的工具占满了名额
- "账号被禁用" → 连锁反应

**纪律**：

1. **诊断脚本必须有终止条件或可外部终止**，不要写 `for {}` 裸循环
2. **记下每个后台任务的 ID，收尾时逐个确认已停**
3. **看到异常流量，第一件事是查"是不是我自己造的"**
4. 诊断工具用完即删二进制，避免被误启动

```bash
# 收尾自检
jobs                       # 列后台任务
ps aux | grep -i <your-tool-name>
```

## 六、凭证/状态文件被覆盖

**症状**：服务突然"全部 503"，账号池为空，但文件明明还在。

**真相**：文件内容被**另一个程序**改写成了不同的格式。

**实战踩坑**：凭证文件的字段名从 `accessKeyId` 变成了 `accessToken` ——
这是另一个同生态项目的写入格式。文件里有**真的** refresh_token，
只是字段名不匹配，导致解析失败、加载 0 个账号。

### 诊断

```bash
# 1) 文件大小/时间是否异常
ls -la auths/
# 2) 字段名是否符合本项目的期望
python -c "import json;d=json.load(open('auths/x.json'));print(list(d.get('auth',{}).keys()))"
# 3) 对比代码里实际读的字段名
grep -n 'json:"' internal/*/credential.go
```

### 预防

- 落盘前**校验必需字段齐全**，不齐就拒绝写（避免半成品文件）
- 日志里记录"谁来加载/保存了凭证"
- 多程序共用目录时，用**不同的文件名前缀**隔离

## 七、资源限额是"每实体"的，不是全局的

读限额配置时必须问清楚：**这个限制是 per-account、per-key 还是 per-instance？**

**实战踩坑**：看到"并发上限 3"以为是全局，实际是**每账号**。
于是：

```
1 个账号 → 3 并发
3 个账号 → 9 并发
```

而"所有账号都满"与"所有账号都不可用"是**两种不同的失败**，
代码里必须区分（见第三节）。

### 检查清单

- [ ] 限额粒度（账号 / key / 实例 / 模型）
- [ ] 满额时是排队还是报错
- [ ] 超额的错误码是什么（便于程序化识别）
- [ ] 限额是否按资源类型区分（不同模型的额度可能独立）

**特别注意**：**不同计费通道的额度可能互相独立。**
实测：账号"积分还剩 5995"，但某个通道的免费额度已耗尽 ——
订阅接口只报积分，看不出免费额度的余量。
**不要拿一个额度数字推断另一个额度是否够用。**

## 八、给用户看的标记要"说人话"

排查完要把结论**沉淀到界面上**，否则下次还得再查一轮。

```json
{
  "id": "deepseek-v4-flash-0731",
  "quota_exhausted": true,
  "quota_reason": "insufficient quota（免费额度已耗尽）",
  "quota_checked_at": "2026-09-12T08:14:00+08:00"
}
```

**三条设计原则**：

1. **只在确认时标记** —— 宁可不标，也不要让用户避开实际可用的资源
2. **带原因和时间** —— "不可用"没有信息量，"免费额度已耗尽 · 08:14 检测"才能指导决策
3. **成功要清除** —— 状态是波动的，实测同一个模型两次探测结果不同

界面上：

- 不可用的项要**视觉压暗**（`opacity:.55`），光加红标签不够醒目
- 给一句**汇总**（"3 个模型额度已耗尽：a、b、c"），省得逐个 hover
- 区分"暂时不可用"与"永久不可用"的措辞

## 九、排障纪律（总结）

1. **先定位层级，再改东西** —— 在每一跳边界抓报文，逐跳对比
2. **入站 ≠ 出站** —— 查上游报错要看**改写后**的报文
3. **不要信 HTTP 状态码** —— 业务错误常常藏在 200 里
4. **分类错误会放大故障** —— 客户端错误罚了账号，一个坏参数能打挂全池
5. **区分"忙"与"坏"** —— 前者该排队，后者该失败
6. **先排除自己的诊断工具** —— 异常流量第一问"是不是我造的"
7. **限额先问粒度** —— per-account 还是 global 决定完全不同的修法
8. **结论要沉淀到界面** —— 否则同一个问题会被查第二遍
9. **改完给验证与回滚** —— 与主技能一致

## 附：一次完整定位的记录（可作模板）

```
症状：客户端持续报 "Stream ended without finish_reason"，但网关日志全 200

Step 1 定位层级
  直连网关（小请求）        → ✅ 正常
  直连网关（带 tools）      → ✅ 正常
  经中转层 → 网关           → ✅ 正常
  结论：不是链路问题，是**特定请求形态**问题

Step 2 抓真实报文
  开入站 dump → 看到客户端实际发的字段
  开出站 dump → 看到网关改写后发的字段
  对比发现：客户端发 max_completion_tokens，上游只认 max_tokens

Step 3 确认根因
  单独构造带该字段的请求 → 复现 400
  去掉该字段            → 正常
  结论确认

Step 4 检查连锁影响
  发现：400 被误分类为"账号故障" → 冷却账号 → 503
  修复：真实状态码解析 + 客户端错误不罚账号

Step 5 加固
  出站字段白名单（防止下一个新字段重演）
  超限值裁剪
  结论写入 /v1/models 标记

Step 6 回归
  用原始报文重放 → 通过
  写测试锁定（含"不该误判"的反例）
```

**关键**：Step 2 的报文对比是整个流程的转折点。
在它之前全是猜测（试了 5 种字段组合都复现不出来）；
在它之后 5 分钟定位。
**先拿证据，再下判断。**
