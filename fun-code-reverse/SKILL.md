# 趣味代码逆向收录（fun-code-reverse）

## 目标与边界

**做**：把用户点名的一段有趣代码——通常是某个大文件里的一小部分——提炼成「**复刻提示词 + 核心片段**」的组合，按规范收录进收藏库。以后想复刻时，把两者一起丢给任何 AI 即可。

**不做**：
- ❌ 不搬运原始噪声代码（只存提炼出的核心片段，10~40 行）
- ❌ 不做生成验证（让 LLM 只看提示词重新生成来验证 = 抽卡，不可靠也无意义；复现可靠性由「提示词 + 片段」配套交付构造性保证）
- ❌ 不写逐行翻译式提示词（提示词管效果与意图，片段管精确机制）
- ❌ 不按案例写进化日志（进化产物只有泛化规则，见第 7 步）

## 核心理念：提示词与片段配套

- **核心片段**（从原代码提炼的 10~40 行）负责「精确机制」：真实变量名、真实参数、真实写法，是复刻时的确定性锚；
- **复刻提示词**负责「效果与意图」：讲清这段机制产出了什么效果、精髓在哪、复刻时注意什么；
- 两者单独都不足以稳定复刻：只有提示词 → 生成方差大；只有片段 → 缺效果语境与意图。配套使用 → 复刻 AI 既有确定性依据又有全局理解。

## 收录目标仓库

`D:\project_GIT\fun-code-collection`

- 每个条目 = 一个子文件夹（**英文小写连字符**命名，名字表达效果主题）+ `README.md` + 核心片段文件
- 根 README 的「📌 收藏清单」表是索引，新条目必须追加一行（子文件夹链接 + 一句话简介 + 类型）
- commit 规范：`add: 新收藏 <snippet-name>`；**不主动 push**，用户明确要求时才推
- 收录前若同名条目已存在，先向用户确认是更新还是新建

## 工作流

### 第 0 步：读经验库（必做）
打开本 skill 目录下的 `playbook.md`，只读与本任务效果类型相关的小节（接收输入 / 提示词写法 / 片段提炼 / 按效果类型 / 收录与仓库），把已验证的通用规则套上去。

### 第 1 步：接收输入
必须拿到三样东西：
1. **代码来源**：文件路径 + 行号范围 / 用户直接粘贴的片段 / 网页 URL；
2. **用户点名的功能点**：用用户原话记下来，这是后续剥噪的唯一依据——**必须来自用户，AI 不得用「代码客观亮点」自作主张替代**，用户的兴趣点常与代码的客观亮点不同；
3. **出处**（可选）：原项目 URL 或「本地文件 X」，用于条目的「来源」节。

缺功能点描述或描述模糊时**必须先问用户**（用原话复述一遍请其确认），不要自行猜测「哪里有趣」。

### 第 2 步：定位与剥噪
- 在原文件中只保留点名功能的执行路径；业务逻辑、无关分支、日志、兼容代码一律视为噪声丢弃；
- 判定标准：把一段代码删掉后，点名功能是否依然成立？成立即噪声；
- 顺手记录：核心机制占原文件的比例，比例越小越说明「逆向收录」这个决定是对的。

### 第 3 步：提炼核心片段
- 从原代码摘出点名功能的最小机制，**10~40 行**，可独立阅读；
- **尽量保留原变量名与真实参数**（这是片段作为确定性锚的价值）；删掉的部分在头部注明「原文件 X-Y 行，节选有删减」；
- 头部注释写明：来源文件与行号范围、「仅作复刻参考」；
- 可以为可读性补注释（变量含义、调用前提），但**不要为可读而改写逻辑**——改写过的片段失去「原代码佐证」资格。

### 第 4 步：写复刻提示词
按「复刻提示词写法规范」（见下文）的固定结构写，提示词中直接引用随附核心片段（如「按 core.bat 第 [2] 段」）。写完自检：
- [ ] 结构齐全且每节都成立；
- [ ] 没有出现原代码的业务上下文（项目名、专有接口名、内部路径）；
- [ ] 与核心片段互相印证、无矛盾、无信息缺口——**做法：假装自己是拿到提示词 + 片段的复刻 AI 通读一遍**，这是替代生成验证的最低成本质量门；
- [ ] 复刻要点 3~6 条。

### 第 5 步：收录入库
1. 在仓库根目录建条目文件夹（小写连字符），写入 `README.md`（模板见下文）与核心片段文件（如 `core.bat`、`core.css`，文件名体现语言）；
2. 根 README「📌 收藏清单」表追加一行；
3. `git add -A` → `git commit -m "add: 新收藏 <snippet-name>"`，不 push。

### 第 6 步：规则级进化（每次任务结束必做）
进化 = 把单次经验**泛化成通用规则**合入 `playbook.md`，让以后所有任务直接受益。**禁止按案例写日志**——案例细节属于收藏库条目，不属于 skill。

执行一次「泛化反思」：
1. 自问：本次有没有一条**去掉项目细节后依然成立**的经验？
   - 反例（不可泛化）：「XX 项目的 bat 要注意编码」——绑定具体项目；
   - 正例（可泛化）：「批处理含中文输出时，复刻提示词必须写明 chcp 65001，否则复刻端默认本地编码导致乱码」——任何同类任务都适用。
2. 通过**写入门槛**（三条全过才写，防止退化成日志）：
   - **可泛化**：规则表述不出现具体项目名、文件名、一次性细节；
   - **可执行**：写成「遇到 X 类情况 → 做 Y」的指令，不是复盘叙事；
   - **非重复**：与 playbook 已有规则不重复——重复则**合并增强原规则**，不新增条目。
3. 写入：合入 playbook 对应小节，格式见 playbook 顶部说明；若经验暴露的是本 SKILL.md 主流程本身的缺陷，**直接修主流程**而不是只记规则；
4. 压缩：playbook 总规则数 >40 或单节 >15 时，合并同类项、淘汰不再适用的规则；
5. **无新规则就不写任何东西**（禁止为了写而写）。

## 复刻提示词写法规范

固定结构（使用时与核心片段一起整段丢给任何 AI）：

```text
【目标】用 <语言/技术> 实现 <形式>，达到 <效果名>。请先读懂随附的核心片段再动手。
【效果】描述现象：用户看到/感受到什么，含关键数值（片段里已有的写「以片段为准」）。
【交互】（如有）输入/操作如何影响表现。
【约束】单文件、无外部依赖、不用框架、目标环境；哪些细节必须与片段一致。
【核心片段导读】随附片段怎么读：先看哪段、精髓在哪几行、为什么这么写、哪些可忽略。
【复刻要点】3~6 条自检项：做到即算复现成功。
```

三条铁律：
1. **分工明确**：提示词管「效果、意图、导读、注意点」，片段管「精确机制与参数」。同一信息不要两处各写一份——片段里有的，提示词引用而不复写，避免不一致。
2. **导读是灵魂**：复刻 AI 未必一眼看懂片段的巧处，提示词要指出「哪里是精髓、为什么这么写」，把隐性知识显性化。
3. **钉死片段没钉死的自由度**：片段缺失的参数（随机策略、默认尺寸、环境假设）必须在提示词里给合理确定值，不留模糊词。

## 条目 README 模板

在收藏库五节模板（这是什么 / 文件清单 / 使用方式 / 值得收藏/复刻的点 / 来源）基础上，逆向收录条目新增「复刻提示词 / 核心片段」两节：

```markdown
# <snippet-name>

> 一句话：这个效果是什么、为什么有趣。

## 这是什么
（大白话讲清效果）

## 文件清单
| 文件 | 说明 |
|---|---|
| core.xxx | 从原代码提炼的最小核心机制 |

## 复刻提示词
> 把本节提示词连同 core.xxx 的内容一起丢给任何 AI（建议新开会话）即可复现。

（fenced block 内放完整提示词，固定结构）

## 核心片段
（内联贴出提炼的 10~40 行代码，注明提炼自哪个文件哪些行；已见于「文件清单」的文件不再重复罗列）

## 使用方式
（复刻怎么用：提示词 + 片段一起发；片段怎么单独参考）

## 值得收藏/复刻的点
（最妙的地方：技巧、模式、坑——包括原代码的隐患）

## 来源
（原链接/出处 + 提炼自哪个文件，注明仅供学习复刻参考）
```

## 注意事项

- 依赖外部服务/数据/特定硬件的效果，片段与提示词只覆盖可复现部分，外部前提写进 README「值得收藏/复刻的点」或「使用方式」；
- 用户一次点名多个功能点 → **每个效果主题一个条目**，不要塞进同一个 README；
- 收录以用户点名为准：AI 自己觉得有趣但用户没点名的功能不收；
- 条目的复现方式是「提示词 + 片段」配套，不承诺提示词单独可用。
