# Epoch Loop（通用外层迭代循环）

> 来源：原 `model-training-mindset` 技能，并入 build。
> 相对本技能目录解析：`epoch-loop.md`。

## 这个文件解决什么问题

`incremental-implementation.md` 的 Increment Cycle 是**单个切片内**的循环，只有前进路径：
Implement → Test → Verify → Commit → 下一片。它知道"失败很痛"（见其 Common Rationalizations），
但**没给出失败时要做什么**。

本文件补上两件事：

1. **失败回退分支**——验证不过就 `reset` 回基线，带失败原因换思路
2. **外层里程碑骨架**——把任务分成"子问题序列"，每个子问题用 epoch 循环攻破，
   子问题之间用 commit 逐级固化

## 什么时候用

**每次实现任务都用，无例外。** 这层循环包在 build 的所有执行形态外面：

| 执行形态 | 是否走 epoch 循环 |
|---|---|
| 多 agent 编排 | ✅ 走（且子代理内部也走） |
| 单 agent（含单文件小改动） | ✅ 走 |
| 多轮长任务 | ✅ 走（这是它原本的主场） |

**小任务怎么走**：子问题序列只有 1 个，epoch 可能只跑 1 轮，
但 **git 基线 + commit 照做**。循环本身是轻的，**基线不可省**。

**唯一的例外**：纯读操作、纯查询、不改任何文件的任务（这类任务没有"回退"的概念）。

> ⚠️ "这次改动太小，不用建基线" 是**明确的红灯**。
> 恰恰是小改动最容易在连续微调中失去可回退点——
> 等你发现改坏了，已经找不到"改之前"在哪里了。

## 三层结构

```text
第三层  子问题衔接     S1 ──commit──→ S2 ──commit──→ S3 ──→ 完成
                       （通过即固化，成为后续的新基线）
                              │
第二层  epoch 循环      ┌─────┴──────────────────────┐
（每个子问题）          │  基线 = 进入本子问题的 commit │
                       │  for epoch in 1..N:          │
                       │    原子改进 → 验证            │
                       │    通过 → commit（新基线）    │
                       │    失败 → reset + 换思路 ★    │
                       └──────────────────────────────┘
                              │
第一层  切片（薄垂直切片 + TDD，见 incremental-implementation.md
        与 test-driven-development.md）
```

**双粒度 checkpoint**（两者都要有）：

| 粒度 | 何时 commit | 作用 |
|---|---|---|
| **子问题级** | 进入/完成每个子问题时 | 里程碑安全网，跨子问题可回退 |
| **轮次级** | 每个 epoch 原子改进通过时 | 单轮安全网，失败时 `reset` 的落点 |

**尺度对应**：

| 外层（本文件） | 内层（incremental-implementation） |
|---|---|
| 子问题（里程碑） | 切片（slice） |
| epoch / 原子改进 | increment |
| 子问题完成标准 | 切片验证（测试通过/构建成功） |
| 子问题级 commit 固化 | 切片级 commit |

## 0. 前置：git 基线

开工前工作目录必须是 git 仓库：

1. 确认：`git rev-parse --is-inside-work-tree`；exit 128 表示不是仓库
2. 不是仓库：`git init`；若目录含大量历史杂物（二进制、旧项目），
   先写 `.gitignore` 把追踪范围收窄到交付物路径，再提交基线
3. 首次 commit = 本任务的起点 checkpoint

> **谁执行 git**：单 agent 任务由你自己做；多 agent 任务**只有 Orchestrator 做**，
> 子代理不碰 git（见 `team-orchestration.md` 的「Git 归属」）。

## 1. 第一层：任务分解（先确认，后执行）

拿到任务，先分解、**不执行**：

- 每个子问题足够小、可独立验证，有明确完成标准（**能由真实命令/真实输出判定**）
- 按依赖排序：前面的完成后，后面的才能做——先易后难，逼近最终目标
- 子问题数量与粒度**不预设**，按"一步一可验证"现场拆

把分解方案给用户确认：

```text
## 分解方案
目标:<一句话总目标>
子问题序列(按依赖序):
  S1 <名称> — 完成标准:<可验证的命令/信号>
  S2 <名称> — 完成标准:<可验证的命令/信号>
  ...
是否确认开始?
```

- 用户确认 → 进入第二层
- 用户要求调整 → **只改分解，不动执行**
- 用户已声明"分解不必预先固定" → 只给总目标 + 总思路，执行时动态拆，
  每个新子问题开工前报出它的完成标准再动手

> **单 agent / 小任务怎么办**：子问题序列就是 `[本任务]` 一项，
> 完成标准就是"验证通过"。**分解这一步不能省**——省掉它就没有"怎样算完成"的判据。

## 2. 第二层：epoch 训练循环（每个子问题）

```text
基线 = 当前状态 git commit（该子问题的 checkpoint）
for epoch in 1..N:
    1. 原子改进：本轮只推进一个点，不一次改一堆
    2. 验证：**只跑 L1 廉价信号**（见下「三级验证」）—— 秒级
    3. 达成/变好 → git commit 保存为新基线，下一轮继续深化
       失败/变差 → git reset --hard 回退到基线，
                   记录失败原因，换思路重试（不原样重试）  ★
直到该子问题达成完成标准 → 此时才跑 L2
```

### ★ 三级验证（省时间的关键）

**核心原则：验证粒度要匹配改动粒度 —— 贵的验证跑最少次。**

```text
❌ 错误（慢）：
   每个 epoch 都跑「全量测试 + 全量构建」
   → 改一个变量也跑 4 分钟
   → 10 个 epoch = 40 分钟，其中 9 次是浪费

✅ 正确（快）：
   每个 epoch   → L1 廉价信号（秒级）
   子问题完成   → L2 核心验证（分钟级）
   交付前一次   → L3 完整门禁（最贵）
```

| 级别 | 何时跑 | 跑什么 | 典型耗时 |
|---|---|---|---|
| **L1 廉价信号** | **每个 epoch** | 编译 / 类型检查 + **只跑与本次改动相关的测试** | 秒级 |
| **L2 核心验证** | **每个子问题完成时** | **受影响包 ∪ 反向依赖包**的测试 + 构建（见下） | 分钟级 |
| **L3 完整门禁** | **交付前一次** | 机器判定型非功能项（供应链/密钥/性能基线/可观测契约） | 最贵 |

**为什么这样不会漏 bug**：

- **L1 查"这次改对了没有"** —— 改动相关的测试足以判定
- **L2 查"有没有碰坏别的"** —— 回归检查，范围 = 改动影响面
- **L3 查"能不能上生产"** —— 机器能判的非功能项，一次就够

> **减少验证 ≠ 少跑测试**，而是**把验证放在对的时机**。

### L1 怎么跑（按改动范围，不跑全量）

```text
1. 看这次改了什么：git diff --name-only
2. 找这些改动对应的测试：
   - Go       → go build ./... + go test ./<改动的包>/...
   - JS/TS    → tsc --noEmit + <测试框架> <相关路径或 -t 过滤>
   - Python   → python -m compileall + pytest <相关文件>
3. 跑那部分 + 编译
```

**⛔ 不许重复验证未变的代码**：

> 如果这一轮**没有改到 X**，就不要重跑 X 的测试。
> 判据：`git diff` 之后，只跑改动涉及的测试。

### ★ L2 怎么跑（受影响包 ∪ 反向依赖包）

**这是本工作流最有效的提速规则** —— 减少绝对工作量，且**不引入新机制**，
**可被事后静态审计**（你能直接比对"改了哪些文件 → 应该跑哪些包"）。

```text
1. git diff --name-only        → 本次改了哪些文件
2. 文件 → 包                    → 改了哪些包
3. 反查：哪些包（直接或间接）依赖这些包
4. L2 测试集 = 受影响包 ∪ 反向依赖包
```

**例**：改 `internal/auth/token.go` → 跑 `internal/auth` + 所有 import 它的包。

#### ⚠️ 三个必须同时满足的安全条件

**① 依赖图现算，不许用缓存**
> 反向依赖索引若来自缓存/构建产物，改了依赖关系但图没重建 →
> 反查是**上一版的**，而你**不会知道**。

**② 改语义/契约时强制全量**

反向依赖图只覆盖**静态 import**。**行为契约改动不走图**：

```text
格式 date 从本地时区改 UTC：
  import 图没变 → affected 仍是那几个包
  但下游有包靠配置串 "format":"local" 约定行为
  → 它的测试会挂，而它不在 affected 集里
```

**规则**：改动涉及**语义 / 协议 / 输出格式 / 默认值 / 配置约定**时 → **跑全量**。

**③ 保留全量逃生口：合并前进 `review` 之前跑一次全量回归**
> **反查算错不会报错，只会静默少测。**
> L2 绿了只代表"**我算出来的那些包**没问题"。所以这条兜底不能省。

> ⚠️ **常见算错形态**（都不报错，只是少测）：
> 依赖通过**字符串/反射/DI 容器**建立（静态图看不见）；
> monorepo 的 `workspace:*` / path alias / tsconfig `paths` 解析不到；
> **测试夹具包**被引用的方向是反的。
>
> 所以：能算准就用它，**算不准或不确定时 → 直接跑全量**，别赌。
>
> 这条与 `incremental-implementation.md` 已有的原则一致：
> *"After a successful run, don't repeat the same command unless the code has changed since."*
> —— 该原则本来就对，只是此前**没有贯彻到 epoch 循环里**。

★ **失败回退分支**：没有它，失败时 agent 会就地打补丁，
越补越乱，最后无法定位是哪处改动破坏的。

**原子改进的定义**：一次 commit 只对应一个可独立验证的改动。
改动大到无法独立验证时，继续拆小。

## 3. 第三层：子问题之间的衔接

- 一个子问题通过后 `git commit` 固化，它成为后续所有工作的**新起点（新基线）**
- 进入下一个子问题，重复第二层循环
- 若下一个子问题**反复失败（≥3 轮同类失败）**，允许回退到上一个已验证子问题的状态，
  重新规划这一步的拆分思路，再进入循环
- 循环往复，直到所有子问题全部完成

## 4. 纪律红线（最高优先级）

1. **绝不跳过验证直接宣称完成**——验证 = 真实命令/真实测试的输出，自我宣称无效
2. **绝不堆积改动**——每轮一个原子改进；堆积后失败将无法定位是哪处改动破坏
3. **回退后带失败原因换思路**——不原样重试
4. **多轮迭代、中途回退是正常过程**——不是失败，不需要为此道歉或解释
5. **任务管理只用 git**——不引入额外的任务管理框架。
   注意边界：**验证用的最小脚本属于"验证"步骤，不受此限**；
   TDD 的测试框架（Jest/pytest/…）同样属于验证工具，也不受限。
   禁的是 git 之外**又一套任务管理系统**。

## 5. 输出模板

### 单轮报告（每个 epoch 结束）

```text
[S<n> 第<k>轮]
原子改动:<本轮改了什么,一个点>
验证:<命令> → <输出摘要>
结果:达成 → commit <hash>(新基线)
    / 失败 → reset 回基线 <hash>,失败原因:<...>,下轮换思路:<...>
```

### 交付清单（收尾）

```text
交付物:
1. <文件路径>(一句话说明)
2. ...
git 历史:<commit 数>,自 <首 hash> 至 <末 hash>,每步可追溯可回滚
```

> 分解方案的模板见第 1 节——**不要在这里重复维护第二份**。

## 6. 注意事项

- 完成标准必须能由"真实可运行的命令/信号"判定，不接受"看起来合理"这类模糊标准
- **进入子问题前的基线 commit 是该子问题的安全网，不可省略**
- 连续 3 轮同类失败，不要在当前子问题内死磕——回退到上一个已验证子问题，重新规划分解
- 报告时如实展示验证输出；发生过失败与 reset 要一并展示，不隐瞒
- 回退用 `git reset --hard <基线 hash>`；未固化的实验性改动不要进 commit，失败直接丢弃
  - ⚠️ **只在工作区里确实只有你自己未提交的改动时才用 `reset --hard`**。
    有子代理并行工作、或有他人未交付成果时，改用定点回退
    （`git checkout -- <本轮涉及的文件>`）。见 `team-orchestration.md` 的「Git 归属」。
- 与 `incremental-implementation.md` 的 Rule 5「Rollback-Friendly」配合：
  那条讲"改动要易于 revert"（事前设计），本条讲"revert 之后怎么想"（事后动作）
- **交付物所在目录不是 git 仓库时**，先为它 `git init` 并提交基线，
  否则本文件的全部纪律在该目标上静默失效（见第 0 节）
