# Plan（计划阶段）

> 对应 `/plan`。核心理念：**Small, atomic tasks**。
> 上游 `define`（要做什么）→ 本技能（**讨论定方案 + 怎么拆**）→ 下游 `build`（开始写代码）。
>
> ★ **本技能是「主脑」在规划期的舞台**：主脑**不一个人拍板** ——
> 技术栈 / 架构 / 内部逻辑 / 链路设计**必须和子代理讨论**，
> 但**最终由主脑拍板**（子代理只有参考性，没有否决权）。
> 规划完成后，**实现也由主脑自己写**（见 `build`）—— **子代理不写代码**。

## 目标与边界

**做**：

- ★ **讨论定方案**：技术栈 / 架构 / 内部逻辑设计 / 第一二步的完整链路 ——
  **不一个人决定**，见下方「讨论机制」
- 把规格拆成 S/M 粒度的可验证任务，每个任务自带验收标准与验证方式
- 画依赖图、定实现顺序
- 每 2–3 个任务插一个检查点
- 产出 `tasks/plan.md` + 建 goal

**不做**：

- ❌ **不写实现代码**（不碰业务文件）—— 但要**讨论并决定技术栈/架构**
- ❌ 不做需求澄清与规格补全（那是 `define`）
- ❌ 不执行任务、不部署、不发版（那是 `build` / `ship`）

> ⚠️ **边界说明**：本技能**允许讨论并决定技术方案**（技术栈/架构/内部逻辑），
> 因为规划期不决策，后面就没机会决策了。
> **但不在此阶段写业务代码** —— 实现统一放在 `build`，由**主脑自己**写。
> **子代理从始至终不写代码**，只做轻量任务（探索/讨论/评审）（见 `../build/subagent-tasks.md`）。

## ★ 讨论机制（全程可用，不限本阶段）

> **讨论不是某个阶段的一次性会议，是贯穿全程的机制。**
> `plan` 和 `build` 都适用 —— **凡是有疑问就讨论**。

**完整机制见 `../build/subagent-tasks.md`** —— 三类任务的分工、派几个、
提示词模板、采纳判据、决策权分层，都在那里。
**本文件不复制一份**，避免两处漂移。

规划期真正需要讨论的是**这几类**：

| 该讨论 | 例子 |
|---|---|
| 技术栈 / 库选型 | 用哪个框架，为什么不用另一个 |
| 架构与模块边界 | 怎么分层、接缝画在哪 |
| 内部逻辑 / 数据流 | 第一二步的完整链路怎么走 |
| 对外契约 | API 形状、错误语义、兼容性 |
| 安全相关横切 | 认证/会话怎么存、密钥从哪来、要不要数据迁移 |

| 不必讨论 | 为什么 |
|---|---|
| 命名 / 目录 / 代码风格 | 品味问题，**直接定，走** |
| 查一下文档就知道的 | 自己查；要读很多文件才答得上来的 → 派**探索档** |

> ★ **主脑提案，子代理给意见，主脑拍板。** 子代理是参谋，**没有否决权** ——
> 不要因为它反对就停住；但**多个子代理独立指向同一风险**时要认真对待。
>
> ⚠️ 也**不要只在「想确认自己是对的」时才讨论** —— 那样会退化成走过场。

## 前置检查（Gate）

开工前必须确认这四条，任一不满足就先补齐，不要硬拆：

1. **规格存在且明确** —— `SPEC.md` / PRD / 用户口述且已复述确认。没有 → 回 `define`。
2. **相关代码已摸清** —— 知道现有目录结构、命名约定、已有模式。
   **要读的文件超过 3 个时派探索档子代理**，别自己硬读 ——
   判断标准是「读它要花掉多少上下文」，不是「能不能查到」
   （见 `../build/subagent-tasks.md`）。
3. **验收命令已知** —— 知道本仓库的测试 / 构建 / lint 命令原文（不是"跑一下测试"）。
4. **能力已盘点** —— 知道本次改动要用的技能/资源从哪来，缺的已明确标出（见步骤 4）。

## 工作流程

### 1. 只读侦察

读规格 + 相关代码，记录：现有约定、组件依赖、风险点、未知项。

面对**陌生代码区域**时，先读 `zoom-out.md`（相对本技能目录），按它的输出格式先给出"模块 + 调用者"地图，再往下做依赖图 —— 不要在没方向感的情况下直接画依赖。

> **此阶段禁止写业务代码。** 计划的输出是文档，不是实现。

### 2. 读详细方法

```text
read planning-and-task-breakdown.md   # 相对本技能目录
```

该文件给出完整方法：依赖图推导、垂直切片、任务结构模板、检查点写法、反模式清单。**本文件只给执行骨架，细节以它为准。**

### 3. 定模块与接缝（有架构改动时）

```text
read codebase-design.md   # 相对本技能目录
```

只要这次改动涉及**新模块、接口重划、或"这块要能测"**，先用深模块词汇（Module / Interface / Implementation / Depth / Seam / Adapter）把接口和接缝定下来，再切任务。接口没定就切任务 = 任务描述里塞满设计决策，必然漂移。

- 找深化机会 → 另读 `DEEPENING.md`
- 想比较两种接口方案 → 另读 `DESIGN-IT-TWICE.md`

纯增量改动（加个字段、改个文案）可跳过本步。

### 3.5 ★ 讨论定方案（重大决策必须做）

**技术栈 / 架构 / 内部逻辑设计 / 链路怎么排 —— 不一个人拍板。**

按顶部「讨论机制」执行：派**讨论档**子代理拿「判断 + 理由 + 风险」，**主脑拍板**。
派几个、提示词模板、采纳判据见 `../build/subagent-tasks.md`。

**必须讨论的议题**（命中任一）：

- 技术栈/库选型（用什么框架、什么存储、什么协议）
- 架构与模块边界（怎么分层、接口怎么切）
- 内部逻辑设计（核心流程、状态机、关键算法）
- **第一二步怎么排**（链路的起点与顺序）

**产出**：把讨论结论写进 `tasks/plan.md` 的「架构决策」段 ——
**含理由与已考虑的风险**，这样 `build` 阶段的子代理不用重新推一遍。

> ⚠️ **不必讨论的**：命名、目录、格式、代码风格（**品味问题直接定**）。
> 讨论要花时间，只用在**真有多个合理选项**的地方。

### 4. 能力盘点（切任务之前）

拆任务之前先回答：**完成这次改动，需要哪些能力？逐个查它们从哪来。**

对每个识别出的能力，按固定顺序查，**查到就停**：

| 顺序 | 查哪里 | 找到后怎么用 |
|---|---|---|
| 1 | 会话可用技能列表（catalog） | `skill <name>` 按名加载 |
| 2 | `build` 的内嵌资源 | `read` 相对路径（**不在 catalog 里**，所以必须显式知道） |
| 3 | 只是知识、不需要工具 | 直接做，不加载任何东西 |
| 4 | 上面都没有 | **才**走 `find-skills` / 联网查 |

> ⚠️ **前两步是穷举本地，不要跳。** 常见错误是直接去 `find-skills` 搜一个
> 本地已经有的技能。`find-skills` 走的是公开技能市场（`npx skills`），
> 它只解决"本地真的没有"，**解决不了"本地有但系统没自动调用"**——
> 后者要靠本步骤的显式盘点。

**为什么需要这一步**：`build` 的 9 个内嵌资源**不在可用技能列表里**（路由技能的子文件不单独注册），
所以系统**不可能**自动调用它们。必须由本步骤从任务描述反查出来，
否则"碰前端该读哪个文件"这件事只能靠运气。

**`build` 内嵌资源速查 → 见 `../build/SKILL.md` 的「第四步」**。
**不要在这里复制一份**——单一来源，避免两处维护漂移。

**盘点结论必须落进每个 task**（见步骤 7 的任务模板），不能只留在脑内。

### 5. 画依赖图

按"底层先建"的顺序：数据模型 → 类型/接口 → 服务端逻辑 → API → 客户端 → UI。
把"谁阻塞谁"写出来，而不是凭感觉排。

### 6. 垂直切片

每个任务端到端交付一条**能跑通的路径**。

- ❌ 横向：任务1 写完整个数据库 → 任务2 写完所有 API → 任务3 写完所有 UI
- ✅ 垂直：任务1 用户能注册（表+API+页面）→ 任务2 用户能登录（…）→ 任务3 用户能建任务（…）

### 7. 写任务

每条任务必须包含：

```markdown
## Task [N]: [一句话标题]

**描述**：这段工作达成什么（一段话）。

**验收标准**：
- [ ] [具体、可测的条件，最多 3 条]
- [ ] [具体、可测的条件]

**验证方式**（分三级，**别把全量测试塞进每轮**）：
- [ ] **L1 每轮跑**：`<编译/类型检查命令>` + `<相关测试的过滤命令>`
- [ ] **L2 子问题完成时**：`<受影响包 ∪ 反向依赖包 的测试命令>` + `<构建命令>`
      ⚠️ 改语义/契约时改跑全量；合并前进 review 前再跑一次全量兜底
- [ ] **L3 交付前**：机器判定型非功能项（供应链/密钥/性能基线/可观测契约）

**需要的技能/资源**（步骤 4 盘点的结论，逐任务落下来）：
| 能力 | 来源 | 状态 |
|---|---|---|
| [要做什么] | `skill: <name>` 或 `read: build/<file>.md` | ✅ 本地 |
| [要做什么] | — | ⚠️ 缺：需联网查 / 需 find-skills |

**依赖**：[Task 编号，或 None]

**预计改动文件/位置**（★ 动手前画边界的依据，必须写到**函数/类/模块**级）：
- `cmd/server/multiprovider.go` → `buildProviders()`
- `cmd/server/multiprovider.go` → `registerRoutes()`
- `internal/auth/token.ts` → 整个文件（新文件）

**规模**：[XS / S / M / L]
```

### 7.1 任务契约只有一份

**队列没了** —— 子代理不写代码，也就不需要「认领」。
所以任务从 plan 到 build **只有这一份格式**，下面这个任务块就是全部。

| 字段 | 谁读 | 作用 |
|---|---|---|
| 标题 | build | 任务标识 |
| 依赖 | build | 定实现顺序（哪几个能先做） |
| 规模（XS/S/M/L） | build | 决定 epoch 的切片粒度 |
| 验收标准 | build | 每个 epoch 的**完成判据** |
| 验证方式 | build | L1/L2 跑什么命令 |
| 预计改动文件/位置 | build | 动手前确认边界，别顺手改到别处 |
| 需要的技能/资源 | build | 该加载哪个子模块 |

> ⚠️ **没有「Result / Blocked」段了** —— 那是子代理交付时填的。
> 现在主脑自己写代码，进度靠**每 epoch 的 commit** 与任务块的勾选状态体现。


> **「需要的技能/资源」三态**：`✅ 本地`（catalog 或 build 资源里已有）、
> `⚠️ 缺`（本地没有，已标明去哪儿找）、`➖ 不涉及`（显式声明本任务不碰该类能力）。
> **不允许留空**——留空等于没盘点。

### 8. 排序与检查点

1. 依赖先满足（地基在前）
2. 每个任务结束时系统仍处于**可运行**状态
3. 高风险任务前置（fail fast）
4. 每 2–3 个任务插一个检查点

```markdown
## Checkpoint: Task 1–3 之后
- [ ] 测试全绿
- [ ] 构建无错
- [ ] 核心用户流端到端可走通
- [ ] 人工确认后再继续
```

### 9. 落盘

**只产出一份东西：`tasks/plan.md`。**

```text
tasks/
  plan.md        ← 总览（人读）+ 任务清单（build 读）
```

**没有 `tasks/queue/` 了。** 队列存在的两个理由是「多 agent 认领」与
「派发前查并发冲突」，而现在**只有一个写者（主脑）** ——
认领没意义，冲突也不可能发生。任务清单直接作为 `plan.md` 的一节：

```markdown
## 任务清单

- [ ] **T1** <标题> · 规模 S · 依赖 —
      验收：<二元可测> ｜ 验证：`<命令>`
      改动：`path/to/file.ts` → `fn()`
- [ ] **T2** <标题> · 规模 M · 依赖 T1
      验收：<二元可测> ｜ 验证：`<命令>`
      改动：`path/to/other.ts`（新文件）
```

**编号即执行顺序**：`build` 总是取**编号最小的未完成任务**，
把它当作下一个**子问题**开工。

> ★ **任务 = 子问题，不是 epoch。** 一个任务内部通常要跑**多个 epoch**
> （每个 epoch = 一个原子改进 + 一次 commit）。
> 所以「任务 T1 完成」意味着 **T1 内部的 epoch 循环收敛了**，
> 而不是「只改了一次」。粒度对应关系见 `../build/SKILL.md` 第三步。

**清单是可追加的（执行中也能加）**：排查、评审、审计发现的新任务，
**不需要重开 plan** —— 直接追加下一个编号。清单是**活的**。

> ⚠️ **「预计改动文件/位置」这一栏仍然要写**，但作用变了：
> 以前是**派发前查并发冲突**（现在没有并发，不再需要），
> 现在是**给主脑自己画边界** —— 动手前确认这次只碰这几处，别顺手改到别处。

- 用 `todo_write` 把任务列表写进当前会话 —— 本轮可见、可跟踪进度
- 若项目指定了外部 tracker（GitHub Issues / Jira / Linear / beads），`tasks/plan.md` 里只保留**有序索引**（ID 或链接），不要两处都维护同一份清单

### 10. 人工确认

把计划交给用户过一遍，确认后才进入 `build`。**不要跳过确认直接开工。**

### 11. 挂 goal（用户确认后立刻做）

**用户一确认，就建 goal —— 不要等 `build` 阶段，不要问用户。**

**为什么在这里建**：`plan` 是必经阶段且躲不掉，而 `build` 的自动路由不保证命中。
把建 goal 挂在 plan 收尾，比指望 `build` 被加载可靠得多。
而且此刻**刚好知道有多少任务** —— 正好用来判断该不该挂。

**判定**：

| `tasks/plan.md` 任务清单里的任务数 | 动作 |
|---|---|
| **≥ 2** | **立刻 `create_goal`** |
| = 1（单轮能收束） | 不建 |

```text
create_goal(objective="<见下方模板>")
```

#### objective 模板（含每轮纪律 —— 这是关键）

**不要把 objective 写成一句话目标。** 它**每轮都会被重新注入上下文**，
是"按任务定制的常驻提示词" —— 把每轮该怎么做一并写进去：

```text
<一句话终点，与验收标准对齐，如"登录模块可用且测试全绿">

【每轮开始先读 tasks/plan.md 的任务清单】
- 有未完成任务 → 取**编号最小的那个**，做一个 epoch：
      原子改进 → L1 廉价验证 → 通过则 commit；失败则回退并换思路
- 全部任务已完成 → **走交付前门禁，四步一步都不能跳**：
      ① 全量回归（跑完整套件，不是 L2 的缩小集）
      ② L3 机器判定（密钥扫描 / 供应链 / 性能基线 / 可观测契约）
      ③ 交给人端到端验收（这一步 agent 做不到，**必须等人**）
      ④ 交 review 做合并前门禁
      走完 ③④ 才 update_goal complete
- 同一阻塞连续 ≥3 轮未解决 → update_goal blocked，写明具体阻塞

【禁止】没有未完成任务却开新一轮 —— 那是空烧轮次。
【禁止】跳过交付前门禁直接 complete —— ①②③④ 缺一不可。
【纪律】每个 epoch 必须 commit；失败回退后**不原样重试**。
```

> ⚠️ **objective 写「怎么推进」，不写「跑到第几轮」。**
> 它是每轮重新注入的**文本**，进度必须每轮现算 ——
> 写死"再做 3 轮"会与实际脱节。

> ⚠️ **为什么纪律要写进 objective**：它不依赖 skill 被加载、不依赖模型记性，
> **每轮唤醒时直接在场**。这是替代 agent preset 的办法 —— 按任务定制，
> 比全局死规则更精准。

**建完之后**：不要向用户确认"要不要继续"，直接进入 `build`。

> 若已经有 goal（例如用户手动挂了），**复用它，不要重复建** ——
> 先 `get_goal` 看一眼。

## 任务规模红线

| 规模 | 文件数 | 处理 |
|---|---|---|
| XS | 1 | ✅ |
| S | 1–2 | ✅ 最佳区间 |
| M | 3–5 | ✅ 最佳区间 |
| L | 5–8 | ⚠️ 尽量再拆 |
| XL | 8+ | ❌ 必须拆 |

**继续拆细的信号**（命中任一条就拆）：

- 预估超过一个专注会话（≈2 小时）
- 验收标准写不出 3 条以内
- 跨两个以上独立子系统（如 auth 与 billing）
- 标题里出现"和 / 并且"（说明是两件事）

## 完成自检（进入 build 前必须全过）

- [ ] 每个任务都有验收标准
- [ ] 每个任务都有验证方式（真实命令或明确的手动步骤）
- [ ] **每个任务的「需要的技能/资源」已填，缺项已标出**
- [ ] **没有把本地已有的技能误判为"需要去找"**（catalog 与 build 资源先穷举过）
- [ ] 依赖已识别且排序正确
- [ ] 没有 XL 任务
- [ ] 没有任务改动超过 ~5 个文件
- [ ] 主要阶段之间都有检查点
- [ ] 已写入 `tasks/plan.md`，并同步到会话 todo 列表
- [ ] 用户已确认计划
- [ ] **任务数 ≥2 时已 `create_goal`，且 objective 内含「每轮先读任务清单」纪律**
- [ ] **每个任务标出了它要过的非功能清单**（安全/性能/可观测/无障碍，按特征挂载；
      任何任务都过 `../_shared/references/definition-of-done.md`）—— 「完成 = 已验证」见该文件的完成定义

## 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 边拆边写代码 | 计划被实现细节绑架，越写越乱 | Plan 阶段严格只读 |
| 任务写成"实现该功能" | 无法判定是否完成 | 强制写验收标准 |
| 横向切片 | 中途没有可运行状态，问题堆积到集成期 | 垂直切片 |
| 没有检查点 | 错误累积到后期才暴露 | 每 2–3 任务插 checkpoint |
| 把设计决策塞进任务描述 | 规格漂移，任务变形 | 设计决策单独放"架构决策"段 |
| 只在脑内规划 | 跨会话/压缩后丢失 | 必须落盘 `tasks/plan.md` |
| 两处维护任务清单 | 清单不一致 | 只留一个权威来源，另一处放索引 |

## 关联资源

按需 `read`，不要全部加载。下列路径**相对本技能目录**解析（技能加载时会注入 `Base directory for this skill: ...`，以它为基准拼接——`read` 不展开 `~`）：

**plan 自身的方法文件**：

- `planning-and-task-breakdown.md` — 完整方法（**必读**）
- `codebase-design.md` — 深模块词汇（Module/Interface/Depth/Seam）与接缝设计；涉架构改动时读
- `DEEPENING.md` — 按依赖类别找深化机会
- `DESIGN-IT-TWICE.md` — 并行设计两版接口再比较
- `zoom-out.md` — 陌生代码区域先出模块地图（步骤 1 用）

**项目级横切清单**（在**步骤 4 能力盘点**时按任务特征挂到对应 task 上，
不要在这里当成无条件清单读）：

| 什么任务挂什么 | 路径 |
|---|---|
| 任何实现（完成定义） | `../_shared/references/definition-of-done.md` |
| 写验收标准、要可测 | `../_shared/references/testing-patterns.md` |
| 碰认证 / 输入 / 数据出口 | `../_shared/references/security-checklist.md` |
| 有性能指标要求 | `../_shared/references/performance-checklist.md` |
| **碰前端 UI** | `../_shared/references/accessibility-checklist.md` |
| 需要日志 / 指标 / 追踪 | `../_shared/references/observability-checklist.md` |
| 要派子代理探索 / 讨论 / 评审 | `../build/subagent-tasks.md` |

> **为什么要求挂到 task 上**：plan 阶段一开始判断不了"有没有 UI"——
> 那是**任务级**属性。等到步骤 4 盘点了具体任务，才知道该挂哪几张清单。
> 无条件全读 = 噪声；漏读 = 横切要求丢失。

> 加载方式：本 harness 用 `read` 读取上述路径（没有 `skill_load` 工具）；这些子文件不注册为独立技能。
