# Epoch Loop（通用外层迭代循环）

> 来源：并入自上游 `model-training-mindset` 方法论（该技能已不存在，此行仅作出处说明）。
> 相对本技能目录解析：`epoch-loop.md`。

## 这个文件解决什么问题

`incremental-implementation.md` 的 Increment Cycle 是**单个切片内**的循环，只有前进路径：
Implement → Test → Verify → Commit → 下一片。它知道"失败很痛"（见其 Common Rationalizations），
但**没给出失败时要做什么**。

本文件补上两件事：

1. **失败回退分支**——验证不过就 `reset` 回基线，带失败原因换思路
2. **外层里程碑骨架** —— 任务序列里每个任务用 epoch 循环攻破，
   子问题之间用 commit 逐级固化

## 什么时候用

**每次实现任务都用，无例外。** 这层循环包在 build 的所有实现外面：

| 场景 | 是否走 epoch 循环 |
|---|---|
| 常规实现（主脑自己写） | ✅ 走 |
| 单文件小改动 | ✅ 走 |
| 多轮长任务 | ✅ 走（这是它原本的主场） |

**小任务怎么走**：任务序列只有 1 个，epoch 可能只跑 1 轮，
但 **git 基线 + commit 照做**。循环本身是轻的，**基线不可省**。

**唯一的例外**：纯读操作、纯查询、不改任何文件的任务（这类任务没有"回退"的概念）。

> ⚠️ "这次改动太小，不用建基线" 是**明确的红灯**。
> 恰恰是小改动最容易在连续微调中失去可回退点——
> 等你发现改坏了，已经找不到"改之前"在哪里了。

## 三层结构

```text
第三层  子问题衔接     S1 ──commit──→ S2 ──commit──→ S3 ──→ 完成
                       （通过即固化，成为后续的新基线）
                              │
第二层  epoch 循环      ┌─────┴──────────────────────┐
（每个子问题）          │  基线 = 进入本子问题的 commit │
                       │  for epoch in 1..N:          │
                       │    原子改进 → 验证            │
                       │    通过 → commit（新基线）    │
                       │    失败 → reset + 换思路 ★    │
                       └──────────────────────────────┘
                              │
第一层  切片（薄垂直切片 + TDD，见 incremental-implementation.md
        与 test-driven-development.md）
```

**双粒度 checkpoint**（两者都要有）：

| 粒度 | 何时 commit | 作用 |
|---|---|---|
| **子问题级** | 进入/完成每个子问题时 | 里程碑安全网，跨子问题可回退 |
| **轮次级** | 每个 epoch 原子改进通过时 | 单轮安全网，失败时 `reset` 的落点 |

**尺度对应**：

| 外层（本文件） | 内层（incremental-implementation） |
|---|---|
| 子问题（里程碑） | 切片（slice） |
| epoch / 原子改进 | increment |
| 子问题完成标准 | 切片验证（测试通过/构建成功） |
| 子问题级 commit 固化 | 切片级 commit |

## 0. 前置：git 基线

开工前工作目录必须是 git 仓库：

1. 确认：`git rev-parse --is-inside-work-tree`；exit 128 表示不是仓库
2. 不是仓库：`git init`；若目录含大量历史杂物（二进制、旧项目），
   先写 `.gitignore` 把追踪范围收窄到交付物路径，再提交基线
3. 首次 commit = 本任务的起点 checkpoint

> **谁执行 git**：**写操作只有主脑**。子代理不执行写 git（只读 `log`/`diff`/`status` 可以），
> 也不改任何文件（见 `subagent-tasks.md` 的「三条禁令」）。

## 1. 第一层：任务序列（就是 `plan` 交下来的那份清单）

**子问题 = `tasks/plan.md` 里的一个任务（`T<n>`）。这里不重新拆一套。**

开工前读一遍清单，确认每一条都满足：

- 足够小、可独立验证，有明确完成标准（**能由真实命令 / 真实输出判定**）
- 依赖顺序正确：前面的完成后，后面的才能做
- 粒度不合适（太小 / 太大）→ **直接改 `plan.md` 的那一行**，不要另开一份分解文档

> ⛔ **不要另写一份「分解方案」。** 上一版这里教人写 `S1 / S2 …` 序列，
> 结果工作流里出现了**第三套任务表示**（`plan.md` 用 `T<n>`、这里用 `S<n>`），
> 而 `build` 只扫 `tasks/plan.md` 的 `- [ ] **T<n>**` ——
> 另写的那份**没有任何消费者，只会与 `plan.md` 漂移**。
> **要改拆法就改 `plan.md` 里那一行**（或作废 + 追加新编号，见 `../plan/SKILL.md` 第 9 步）。

> ⛔ **不要为粒度问题停下来等人确认。** 怎么拆是**实现细节，属内部决策**
> （见 `subagent-tasks.md` 的「决策权分层」）—— 计划本身已经在 `plan` 收尾时由人确认过了。
> **停下来问 = 把该自己解决的问题推给人，而且会把整个 build 卡在起点。**

> ⚠️ **但有两种情况必须告知人**（这才算外部事项）：
> - 阅读时发现**规格有歧义**或**范围变了** → 先澄清，别猜着往下做
> - 发现要动**不可逆的东西**（删数据 / 改公开 API / 数据迁移）→ 先告知，再继续
>
> 这属于「不可逆操作：先告知人」——**告知不等于等回复**，别停下来等。

> **只有一个任务时**：任务序列就是 `[本任务]` 一项，完成标准就是它的验收标准。
> **「先读清单、确认完成判据」这一步不能省** —— 省掉它就没有「怎样算完成」的判据。

## 2. 第二层：epoch 训练循环（每个子问题）

```text
基线 = 当前状态 git commit（该子问题的 checkpoint）
for epoch in 1..N:
    1. 原子改进：本轮只推进一个点，不一次改一堆
    2. 验证：**只跑 L1 廉价信号**（见下「三级验证」）—— 秒级
    3. 达成/变好 → git commit 保存为新基线，下一轮继续深化
       失败/变差 → git reset --hard 回退到基线，
                   记录失败原因，换思路重试（不原样重试）  ★
直到该子问题达成完成标准 → 此时才跑 L2
```

### ★ 三级验证（省时间的关键）

**核心原则：验证粒度要匹配改动粒度 —— 贵的验证跑最少次。**

```text
❌ 错误（慢）：
   每个 epoch 都跑「全量测试 + 全量构建」
   → 改一个变量也跑 4 分钟
   → 10 个 epoch = 40 分钟，其中 9 次是浪费

✅ 正确（快）：
   每个 epoch   → L1 廉价信号（秒级）
   子问题完成   → L2 核心验证（分钟级）
   交付前一次   → L3 完整门禁（最贵）
```

| 级别 | 何时跑 | 跑什么 | 典型耗时 |
|---|---|---|---|
| **L1 廉价信号** | **每个 epoch** | 编译 / 类型检查 + **只跑与本次改动相关的测试** | 秒级 |
| **L2 核心验证** | **每个子问题完成时** | **受影响包 ∪ 反向依赖包**的测试 + 构建（见下） | 分钟级 |
| **L3 完整门禁** | **交付前一次** | 机器判定型非功能项（供应链/密钥/性能基线/可观测契约） | 最贵 |

**为什么这样不会漏 bug**：

- **L1 查"这次改对了没有"** —— 改动相关的测试足以判定
- **L2 查"有没有碰坏别的"** —— 回归检查，范围 = 改动影响面
- **L3 查"能不能上生产"** —— 机器能判的非功能项，一次就够

> **减少验证 ≠ 少跑测试**，而是**把验证放在对的时机**。

### L1 怎么跑（按改动范围，不跑全量）

```text
1. 看这次改了什么：git diff --name-only
2. 找这些改动对应的测试：
   - Go       → go build ./... + go test ./<改动的包>/...
   - JS/TS    → tsc --noEmit + <测试框架> <相关路径或 -t 过滤>
   - Python   → python -m compileall + pytest <相关文件>
3. 跑那部分 + 编译
```

**⛔ 不许重复验证未变的代码**：

> 如果这一轮**没有改到 X**，就不要重跑 X 的测试。
> 判据：`git diff` 之后，只跑改动涉及的测试。

### ★ L2 怎么跑（受影响包 ∪ 反向依赖包）

**这是本工作流最有效的提速规则** —— 减少绝对工作量，且**不引入新机制**，
**可被事后静态审计**（你能直接比对"改了哪些文件 → 应该跑哪些包"）。

```text
1. git diff --name-only        → 本次改了哪些文件
2. 文件 → 包                    → 改了哪些包
3. 反查：哪些包（直接或间接）依赖这些包
4. L2 测试集 = 受影响包 ∪ 反向依赖包
```

**例**：改 `internal/auth/token.go` → 跑 `internal/auth` + 所有 import 它的包。

#### ⚠️ 两个必须同时满足的前提

**① 依赖图现算，不许用缓存**
> 反向依赖索引若来自缓存/构建产物，改了依赖关系但图没重建 →
> 反查是**上一版的**，而你**不会知道**。

**② 改动影响到「非 import」的约定时，把范围算大**

反向依赖图只覆盖**静态 import**。**行为契约改动不走图**：

```text
格式 date 从本地时区改 UTC：
  import 图没变 → affected 仍是那几个包
  但下游有包靠配置串 "format":"local" 约定行为
  → 它的测试会挂，而它不在 affected 集里
```

**规则**：改动涉及**语义 / 协议 / 输出格式 / 默认值 / 配置约定**时 →
**把范围算大**（把配置 / 契约的下游也拉进来，必要时整棵子树）。
⛔ **不是跑全量。**

> ⛔ **本工作流不跑全量测试套件 —— 范围只由 diff 决定，永远。**
> 算不准就把范围**放**大，别切换模式。全量套件是**人**在最后那次端到端里
> 自己决定要不要跑的事，不是 agent 的例行步骤。

> ⚠️ **常见算错形态**（都不报错，只是少测）：
> 依赖通过**字符串 / 反射 / DI 容器**建立（静态图看不见）；
> monorepo 的 `workspace:*` / path alias / tsconfig `paths` 解析不到；
> **测试夹具包**被引用的方向是反的。
>
> 所以：**逐条检查这几类**，命中就把范围放大。
> **这就是「不跑全量」的对价 —— 用一次人工排查，换掉一次全量跑。**

> 这条与 `incremental-implementation.md` 已有的原则一致：
> *"After a successful run, don't repeat the same command unless the code has changed since."*
> —— 该原则本来就对，只是此前**没有贯彻到 epoch 循环里**。

★ **失败回退分支**：没有它，失败时 agent 会就地打补丁，
越补越乱，最后无法定位是哪处改动破坏的。

**原子改进的定义**：一次 commit 只对应一个可独立验证的改动。
改动大到无法独立验证时，继续拆小。

## 3. 第三层：子问题之间的衔接

- 一个子问题通过后 `git commit` 固化，它成为后续所有工作的**新起点（新基线）**
- 进入下一个子问题，重复第二层循环
- 若下一个子问题**反复失败（≥3 轮同类失败）**，允许回退到上一个已验证子问题的状态，
  重新规划这一步的拆分思路，再进入循环
- 循环往复，直到所有子问题全部完成

## 4. 纪律红线（最高优先级）

1. **绝不跳过验证直接宣称完成**——验证 = 真实命令/真实测试的输出，自我宣称无效
2. **绝不堆积改动**——每轮一个原子改进；堆积后失败将无法定位是哪处改动破坏
3. **回退后带失败原因换思路**——不原样重试
4. **多轮迭代、中途回退是正常过程**——不是失败，不需要为此道歉或解释
5. **任务状态只落在两处：git 历史 + `tasks/plan.md`**——不引入第三套任务管理系统。
   - **git 历史** = 不可否认的进度证据（每个 epoch 一个 commit）
   - **`tasks/plan.md` 的勾选** = 下一轮该做哪个（取编号最小的未勾选 **`- [ ] **T<n>**`**；
     Checkpoint / 待决问题 / 完成自检的勾选框**不算任务**）
   - **会话内 `todo_write`** 只是当轮的可见列表，**不是持久状态** —— 跨会话靠 `plan.md`
   - **goal 的 objective** 每轮重新注入，是**纪律的载体**，不是任务清单本身
   注意边界：**验证用的最小脚本属于「验证」步骤，不受此限**；
   TDD 的测试框架（Jest/pytest/…）同样属于验证工具，也不受限。
   禁的是**让任务状态只活在第三套系统里** —— 外部 tracker（Jira / beads / 自建状态机…）
   只能是 `tasks/plan.md` 的**镜像**，绝不能替代它。`build` 只扫 `tasks/plan.md` 里的
   `- [ ] **T<n>**`；勾选一旦搬进 tracker，它就**没有输入**，会静默判定「全部完成」并收工。

## 5. 输出模板

### 单轮报告（每个 epoch 结束）

```text
[S<n> 第<k>轮]
原子改动:<本轮改了什么,一个点>
验证:<命令> → <输出摘要>
结果:达成 → commit <hash>(新基线)
    / 失败 → reset 回基线 <hash>,失败原因:<...>,下轮换思路:<...>
```

### 交付清单（收尾）

```text
交付物:
1. <文件路径>(一句话说明)
2. ...
git 历史:<commit 数>,自 <首 hash> 至 <末 hash>,每步可追溯可回滚
```

> 任务清单的权威是 `tasks/plan.md` —— **不要在这里、或任何地方，另维护第二份**（见第 1 节）。

## 6. 注意事项

- 完成标准必须能由"真实可运行的命令/信号"判定，不接受"看起来合理"这类模糊标准
- **进入子问题前的基线 commit 是该子问题的安全网，不可省略**
- 连续 3 轮同类失败，不要在当前子问题内死磕——回退到上一个已验证子问题，重新规划分解
- 报告时如实展示验证输出；发生过失败与 reset 要一并展示，不隐瞒
- **回退分三步，缺一个就会污染下一轮**
  1. **先把 `tasks/plan.md` 摘出去** —— 它记着勾选与执行中追加的新任务，
     **不属于「本轮代码改动」**。回退前先 `git commit tasks/plan.md` 单独固化它
     （或用 `git stash push tasks/plan.md` 保住）。
     ⚠️ 不这么做，`reset --hard` 会把本轮的勾选和新任务**一起吞掉**，
     下一轮重做已完成的工作，而且**不报错**。
  2. **定点回退代码** —— `git checkout -- <本轮改动的代码文件>`（显式列出，不含 plan.md）。
     只有确认工作区里**只剩本轮代码改动**时，才用 `git reset --hard <基线 hash>`。
  3. **清理本轮新建的未跟踪文件** —— ⚠️ **`reset --hard` 与 `checkout --` 都不删未跟踪文件**，
     本轮新建的脚本/文件会留在工作区污染下一轮，而你会以为已经回干净了。
     先 `git clean -n -- <路径>` 空跑看清楚，再 `git clean -f -- <路径>`。
     ⛔ **不要用 `git clean -fdx`** —— 它会连 `.env`、构建产物、别人的东西一起删。
  见 `subagent-tasks.md` 的「三条禁令」（子代理不改文件，所以工作区里只会有主脑自己的改动）。
- 与 `incremental-implementation.md` 的 Rule 5「Rollback-Friendly」配合：
  那条讲"改动要易于 revert"（事前设计），本条讲"revert 之后怎么想"（事后动作）
- **交付物所在目录不是 git 仓库时**，先为它 `git init` 并提交基线，
  否则本文件的全部纪律在该目标上静默失效（见第 0 节）

## 7. DSH 等待语义速查（实测校正）

> **为什么在本文件**：本节是**运行时事实**，不是编排方法论。
> 其他技能也用得上，故不放在某个技能文件里独占。

| 工具 | 是否阻塞当前轮 | 能否本轮拿到结果 | 备注 |
|---|---|---|---|
| **`subagent(run_in_background: false)`** | ✅ **阻塞** —— 不返回直到跑完 | ✅ **能** | 同一轮发多个 = **真并行**、一起返回 |
| `subagent(run_in_background: true)` | ❌ 立即返回 id | ❌ **不能**（靠后续轮次推送） | **没有等待接口** |
| `workflow(...)` | ✅ 前台阻塞 | ✅ 能 | 大批量 + 脚本化汇总 |
| ~~`job_output(job_id, wait: true)`~~ | ⚠️ 只对 **job id** | — | **实测对子代理无效**（`Error: unknown job`） |
| `send_message(agent_id, …)` | 不阻塞（仅投递） | — | 中途 steer；也可唤醒 idle 子代理 |
| `interrupt_agent(agent_id)` | 立即返回（请求取消） | — | 对**还在跑**的有效；对已停滞的没用 |

### ⛔ `false` 没有超时 —— 这才是选模式的真正依据

**实测：`subagent` 工具没有声明 `timeoutMs`。** DSH 的工具超时策略是
`if (timeoutMs === void 0) return next()` —— **只对声明了限额的工具生效**。
本机对照：`pwsh` / `bash` / `fs-search` / `jobs` / `web` 都声明了，**`subagent` 没有**。

推论（重要）：

- **`false` 停滞 = 卡死在调用里** —— 没有超时、没有取消点、没有降级路径。
- **`true` 停滞 = 只损失那一份输入** —— 回合照常继续，结果永远不来，但你**知道**。

实测停滞率（本次会话 33 次派发，全为默认 `true`）：**31 completed / 2 stalled**。
那 2 个是**同一批、同一秒**停的（都停在 9 行、有 `turn/start` 无 `turn/end`）——
所以这更像**批次级的基础设施抖动**，不是每次派发独立的 6%。**换模式躲不掉它。**

### 选模式：判据是「这一步要不要它们**一起**到手」，不是「我忙不忙」

**`false` 唯一不可替代的能力是「汇合语义」（join / barrier）**：
同一轮发 N 个，**一次返回、结果同时到手** —— 你才可能当场横向比较、
或立刻据此写代码。`true` 给不了这个：结果会散落在后续各轮，
你得自己数 id 拼装，等于**用更贵的轮次开销，重造 `false` 免费提供的东西**。

| 这一步的形态 | 用 | 为什么 |
|---|---|---|
| **要 N 个结果一起到手才能比较 / 合并 / 拍板**（多样性派发 3–4 个方案；探索 + 讨论后当场决策） | **`false`**（同一轮全发出去） | 只有它有 barrier；缺了它，「横向对比」退化成「分四次单点阅读」 |
| **结果不在本步关键路径上**（背景调研、往后才用） | **`true`** | 不占本轮；代价是要自己收集 |

> ⚠️ **别用「我忙不忙」当选模式的依据** —— 那筛的是空闲度，不是失败代价。
> 也**别用「人在等」当依据** —— 派发那一刻你判断不了对方急不急，
> 拿它当例外，等于给 `false` 补一个虚构的紧迫感。

**两种模式的失败模式正好相反 —— 这才是要权衡的东西：**

| | `false` | `true` |
|---|---|---|
| 停滞时的表现 | **卡死在调用里**（**可见**：你就停在那儿） | **静默腐烂**（**不可见**：什么都不来） |
| 有超时吗 | ❌ 没有（`subagent` 未声明 `timeoutMs`） | —— |
| 能当场诊断吗 | ❌ 卡在调用里，**读不了日志** | ✅ 可以去读它的会话日志 |

> ⛔ **`true` 的静默腐烂是它最危险的属性。** 实测那次两个停滞的子代理，
> **没有收到任何通知、任何错误** —— 只有主动去翻会话日志才发现。
> **这不是「少了一个结果」，是「你不知道自己少了一个结果」。**

**派发台账（用 `true` 时的硬要求）**：

```text
每个 true 派发记一行：  <agent_id> → <要它干什么> → 结果到了吗
收到通知就划掉；到「该用它」的那一步，主动对着台账点一遍 ——
没划掉的，就是静默丢失：当场补派，或标记 lost 继续，绝不无限等。
```

> ★ **台账把「静默腐烂」变成「可发现」。** 没有它，`true` 丢结果是无声的 ——
> 你会带着一个自己都不知道的空缺往下做。

### 停滞怎么办（runbook —— 两种模式都要防）

**识别签名**（子代理会话持久化在磁盘上，可读）：

```text
日志停在固定行数（实测停在 9 行）
+ 有 turn/start 但无 turn/end
+ 无后续写入
```

用它判断「它到底还在跑，还是已经死了」—— **别干等，也别凭感觉重派**。

**恢复顺序**：

1. **不原地重试** —— 没有重试接口；`false` 更是连退出的机会都没有。
2. **同一任务换更窄的 prompt 重派一次**（切小、去掉可选要求）。
3. **第二次仍停 → 标记 lost，继续往下做** —— 当作「这次没拿到独立意见」，
   而不是「必须等到它」。**绝不无限等。**
4. **整批全停 → 是派发层问题，不是任务问题** —— 改成**串行、逐个**派，
   而不是加大并发。

### 实测记录（本机验证，勿凭推断覆盖）

```text
① 同一轮发 2 个 subagent(run_in_background: false)，各 sleep 20s：
     A start=14:14:07.978 end=14:14:27.995
     B start=14:14:08.620 end=14:14:28.645
   → start 差 0.64s / end 差 0.65s / 总耗时 20s（非 40s）
   → 结论：默认模式天然并行，且全部完成后才返回

② subagent(run_in_background: true) 返回：
     "started subagent 4d5d7a4f-..."
   → 只给 id，无结果；结果随后由 runtime 推通知

③ job_output("cf1c9d11-...", wait:true) 其中 id 来自 subagent：
     Error: unknown job cf1c9d11-...
   → 结论：subagent id ≠ job id，job_output 不能用于子代理

④ 某次会话 33 次派发（全为默认 true）：31 completed / 2 stalled
   停滞样本签名：9 行、有 turn/start 无 turn/end、无后续写入（同批同时停）
   → 结论：停滞是批次级的，不是独立随机；且 subagent 未声明超时
```

**关键区分**：`job_output` 的 id 来自「**启动了后台作业的那个工具**」
（例如 `pwsh(run_in_background: true)`）；而 `subagent` 返回的是 **subagent id**，
**两者不通用**。
