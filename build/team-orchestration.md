# Team Orchestration（多智能体编排）

> 来源：原 `agent-team-orchestration` 技能，并入 build。
> 相对本技能目录解析：`team-orchestration.md`。

## 什么时候读这个文件

**这是 build 的默认路径。** 除非任务命中降级规则（见 `SKILL.md` 第一步），
否则默认按多 agent 编排推进——主会话做 Orchestrator，实现交给 Builder 子代理。

触发信号（命中任一即保持多 agent，不降级）：

- 改动跨文件 / 跨模块，需要多个 Builder 分工
- 需要并行探索（同时查多份资料、多个模块、多个方案）
- 需要独立评审（产出需要另一双眼睛签字）
- 长任务挂持久目标（goal）且需要委派

**唯一的降级条件**（三条全满足才降级为单 agent，且必须显式说明理由）：

- 改动集中在一个文件内的一个函数/方法
- 不需要并行探索
- 不需要独立评审（改动足够机械、对错一眼可判）

> 默认多 agent 的含义是**默认按多 agent 思考**，不是默认制造开销。
> 降级是设计的一部分，但**降级要留痕**——让用户看得见、能推翻。

## ⚠️ Git 归属：只有 Orchestrator 碰 git

**这是硬规则。** 子代理产出文件，Orchestrator 独占全部 git 操作。

| 动作 | 谁做 | 为什么 |
|---|---|---|
| `git init` / `.gitignore` / 建基线 commit | **Orchestrator** | 基线是全队共享的唯一回退点 |
| `git add` / `git commit` | **Orchestrator** | 只有它看得见全队状态 |
| `git reset --hard` | **Orchestrator** | **破坏性操作，见下** |
| 读文件、写文件、跑测试 | 子代理 | 这是它们该干的 |

**子代理不执行任何 git 命令。** 委派提示词里要**明确写这一条**，
否则子代理会自己 `git add -A && git commit`，在并行时制造交错历史甚至锁冲突。

**子代理怎么交付**：按约定路径写产物文件 + 在最终回复里报告
「改了哪些文件 / 怎么验证 / 已知问题」。**commit 由 Orchestrator 在 join 之后统一做。**

### 并行时的两条禁令

**① 禁止让多个子代理同时改同一工作区的同一批文件。**

同一工作区里，B 看到的树可能是 A 改了一半的中间态 → **B 的验证结论对 A 的改动不成立**。
要么**串行**（一次只开一个写同一目录的子代理），要么**分区**
（各自独立子目录，或各自 `git worktree`）。

**② 禁止在有子代理正在工作时执行 `git reset --hard`。**

`reset --hard` 会**丢弃整个工作区的未提交改动**——包括其他子代理正在写、
还没交付的成果。这不是"回退自己这一轮"，是**毁掉别人的工作**。

**正确顺序**：

```text
1. 所有子代理 join 完成（本轮工作区不再有并发写入）
2. 检查产物 → 记录哪些文件变了（git status）
3. 验证通过 → git add <本轮产物> && git commit —— 原子提交，不 add -A 卷入无关改动
4. 验证失败 → 确认没有他人未交付的成果后，才允许 reset
              或更安全：git checkout -- <本轮涉及的文件> 做定点回退
```

> ⚠️ **优先用定点回退**（`git checkout -- <file>` / 手工撤销本轮改动），
> 只有在本轮改动确实是工作区里唯一未提交内容时，才用 `reset --hard`。

### 串行场景（单 agent 或只有一个写入者）

只有一个写入者时，`epoch-loop.md` 的"失败 → `reset --hard` 回基线"是安全的——
那时工作区里确实只有你自己的改动。**并行的存在与否，决定 `reset --hard` 安不安全。**

## ⚠️ 与 build 本体的关系（先读这条）

两者**不是冲突，是分层**：

| | 本文件（编排层） | build 本体（执行层） |
|---|---|---|
| 回答 | **谁**来写、谁审、怎么交接 | 代码**怎么**写才对 |
| 你的角色 | **Orchestrator**（路由与跟踪，不亲自 build） | **Builder**（亲自切片实现） |
| 生效范围 | 编排者会话 | **每个子智能体的会话内部** |

**关键**：Orchestrator 不亲自干活，但**每个 Builder 子智能体内部仍按 build 的切片 + TDD 流程执行**。
子智能体的委派提示词里应当带上 build 的执行纪律（见「委派提示词模板」）。

> 同一时刻只有一条分支被激活：你是编排者 → 读本文件；你要亲手写代码 → 读 build 本体。
> 不要同时套用两套角色指令。

## 角色

每个 agent 一个主角色，重叠会导致混乱。

| Role | Purpose | 模型倾向 |
|---|---|---|
| **Orchestrator** | 路由工作、跟踪状态、做优先级判断 | 高推理模型（承担判断） |
| **Builder** | 产出工件——代码、文档、配置 | 机械性工作可用更省的模型 |
| **Reviewer** | 验证质量、对缺口提出反对 | 高推理模型（能抓住 Builder 漏掉的） |
| **Ops** | 定时任务、站会、健康检查、派发 | 可靠前提下最省的模型 |

## 决策权分层（谁定什么）

**核心原则：内部的事 agent 自己定；外部的事交给人。**

人的注意力是稀缺资源。**动不动就上报 = 把该自己解决的问题推给人。**

### 划分

```text
┌──────────────────────────────────────────────┐
│ 内部 —— agent 自己讨论决定，不用问人            │
│   · 技术栈 / 库选型     · 架构 / 模块划分        │
│   · 实现方式 / 算法     · 目录结构 / 命名        │
│   · 测试框架           · 函数怎么写             │
├──────────────────────────────────────────────┤
│ 外部 —— 交给人                                │
│   · 要什么功能（范围）  · 端到端验收（真人测）    │
│   · 不可逆操作（告知，见下）                     │
└──────────────────────────────────────────────┘
```

### ⛔ 不要问人的情况（这是治"什么都来问"的关键）

> ❌ 用哪个库 / 什么架构 / 变量怎么命名 / 目录怎么分 /
> 用哪个测试框架 / 这个函数怎么写 / 选什么算法
>
> **以上一律自己定，不要上报。**

| ✅ 该问人 | ❌ 不该问人 |
|---|---|
| 功能范围变了 | 用哪个库 |
| 端到端验收 | 什么架构 |
| 不可逆操作确认 | 变量/目录/文件命名 |
| 需要人给权限/资源 | 用哪个测试框架 |
| 业务规则有歧义 | 实现细节怎么写 |

### 内部决策怎么定：**讨论**

```text
遇到内部决策
  │
  ├─ 是「品味问题」吗？（命名 / 目录 / 代码风格 / 格式）
  │    └─ 是 → **直接选一个，走。不讨论。**
  │            （这些没有客观对错，讨论纯属浪费时间）
  │
  └─ 不是（影响功能的内部决策）
       └─ 开讨论：
            ① 提案者给方案 + 理由
            ② 子代理给意见（**可以反对，也可以同意**）
            ③ 双方同意 → ✅ 定
               有分歧   → 改方案再议
            ④ 2 轮仍无共识 → 才上报给人
```

**规则要点**：

- **谁提案谁先给理由**，不要只丢一个结论
- 子代理**可以同意也可以反对** —— 不强制它唱反调
- **双方一致即可定** —— 不需要走审批
- **2 轮上限**：两轮还吵不出结果，说明没有明显更优解，**继续吵是浪费**，交给人拍板

> **参考零成本的客观信号**：如果编译/测试**已经跑过**（红了就是红了），
> 顺手看一眼是应该的 —— 这不叫"验证流程"，是不假装看不见已知事实。
> **但不要为了决策专门去写检查** —— 内部决策走讨论。

### ★ 不可逆操作：先告知人（不必等回复）

| 操作 | 处理 |
|---|---|
| 数据迁移 / 删数据 / 公开 API 变更 / 改他人负责的代码 | **先告知人**，知会后继续 |

**为什么**：不可逆的错，事后修成本极高。
**告知不是为了征求许可，是为了让人有机会喊停。**

> ⚠️ **`blocked` 不是上报内部决策的出口。**
> 内部问题（选型/架构/实现）**没有讨论就标 `blocked`** = 把该自己解决的问题推给人。
> 只有**外部问题**（功能范围、端到端验收、权限）或**2 轮无共识的内部争议**才该上报。

## 默认编排：一次标准派发

默认路径不是"派一堆 agent"，而是**有形状的两/三步**。最小可用形态：

```text
1. 形态判定       写一行 [形态判定]，确认保持多 agent（或降级并说明理由）
2. ★ 孤儿检查     扫 claimed/：认领者还活着吗？
                  不在了 → 按「孤儿任务恢复」处置（回 pending / 进 review）
                  ⚠️ 崩溃会伪装成"在等"，这一步防的就是它
3. 读任务队列     从 tasks/queue/ 取全部「可认领」任务（依赖已满足的）
                  ⚠️ 是"全部"，不是"一个"
4. 确认 goal      已挂则复用；多轮/多批次且没挂 → create_goal
5. ★ 有疑问？     拿不准 / 有多个合理选项 → 派**讨论型**子代理（轻、秒级）
                  重大决策派 2 个，日常疑问派 1 个 → 主脑拍板
                  ⚠️ 讨论不必等，也别为"确认自己对"而讨论
6. ★ 冲突扫描     本轮要派的 N 个任务，列出各自「预计改动文件/位置」并两两比对：
                  同一文件同一函数 → **合并**；同文件不同函数 → 并行但划定边界
                  无交集 → 安全并行
7. 分配 + 扇出    给这 N 个任务逐个标记认领者，**同一轮发 N 个**：
                  subagent(run_in_background: false) × N（N 上限 5）
                  每个都是**一次性执行型**（一任务一 agent，用完不复用）
8. 收敛           默认(false) → 工具返回即已收敛，无需额外动作
                  用了(true)  → 无事后等待接口，结果靠推送（下一轮）
9. 更新队列       通过 → 标 done + commit hash；失败 → 回退到 pending
10. ★ 重算可认领  本轮标 done 后，**立刻重算可认领集**：
                  有新增解锁的 → **本轮直接追加派发**，不要等下一轮
11. 评审          命中触发条件（不可逆/安全/接口/需评审/有不确定）的任务：
                  任务移入 review/，派**另一个**子代理评审（见「评审门禁」）
12. 交棒          汇总产物、更新 goal 状态、决定下一轮
```

> ★ **第 5 步"有疑问就讨论"是全程可用的** —— 不只在开头。
> 任何时候拿不准都可以插入这一步；但它**必须是快的**（讨论型提示词很轻）。
>
> ★ **第 2 步防的是最危险的静默失败**：崩溃后 `claimed/` 有孤儿、
> 但没有活着的子代理 —— 看起来像"在等"，实际永远等不到。
>
> ★ **第 6 步是派发的第一道闸门。** 冲突在**派发前**发现 = 一行合并；
> 在**运行时**发现 = 烧掉好几轮。（实证：三个任务同写一个装配文件 → 编译间歇红）
>
> ★ **第 10 步是依赖任务的关键。** 一轮派 N 个 → 其中一个完成 → 它解锁了下游任务
> → **立刻补派**，而不是"等下一轮"。否则依赖链会把并行度压成每轮 1 个。

### ⛔ 派发数量规则：有多少派多少（上限 5）

**这是命令，不是建议。**

```text
可认领任务数 N = tasks/queue/pending/ 里
                 depends_on 与 stacks_on **全部已在 done/** 的项数

  N = 0  → 不派。去 join 在跑的，或判断是否收工
  N = 1  → 派 1 个（允许，但见下方"线性链"警示）
  N ≥ 2  → 同一轮把这 N 个全部派出（N > 5 时派 5 个，其余下一轮）
```

| 可认领数 | 本轮派几个 |
|---|---|
| 0 | 0（去 join / 收工） |
| 1 | 1 |
| 2–5 | **全部**（2 就派 2，5 就派 5） |
| >5 | 5（上限），其余下一轮 |

### 分批放行：可认领 > 5 时怎么走

队列有 20 个任务、上限 5 —— **不是"派 5 个然后傻等"，而是流水线**：

```text
第 1 批：取编号最小的 5 个 → 派
   ↓ 其中一个 done
   ↓ 立刻重算可认领集（含新解锁的）
   ↓ 在跑数 < 5 → **马上补 1 个进来**，保持 5 个在跑
   ↓ 重复，直到 pending 空
```

**规则**：**保持"在跑数 = min(5, 可认领数)"**，而不是"一批做完再开下一批"。

| 情形 | 做法 |
|---|---|
| 可认领 > 在跑槽位 | 补派，填满到 5 |
| 任务 done 解锁了下游 | 立刻补派那个下游（见「依赖处理」第 3 节） |
| 有任务失败回退到 pending | 它重新变成可认领，可再派（换思路，不原样重试） |
| 全部 claimed、无 pending | 停止派发，等收敛 |

> ⚠️ **不要"等一批全做完再开下一批"** —— 那样最慢的一个会拖住所有槽位。
> 谁先完成谁先让位，**流水线式补位**。

> ⚠️ **只派一个是常见也最没意义的错误。** 它把多 agent 退化成单 agent，
> 却仍然付了提示词冷启动成本 —— **比不派更差**（不派至少省了开销）。
> 除非队列里真的只剩 1 个可认领任务，否则**不许只派一个**。

> ⚠️ **N = 1 的两种情形要分清**：
> - **队列里真的只剩 1 个任务** → 正常
> - **因依赖链导致只有 1 个解锁** → 合规但**并行度=1**，应去看
>   「依赖处理」第 4 节（该切宽任务，而不是等）

**实测依据（本机）**：同一轮并发 5 个 `subagent(run_in_background: false)`，
5 个在 2.6 秒内全部启动，总耗时 25 秒（而非 125 秒）——**平台没有并发瓶颈**。

**解锁补派**：本轮每有一个任务 `done`，**立刻重算 N 并补派** ——
详见「依赖处理」第 3 节。不要等下一轮。

> **独立工作放在哪**：用默认的 `false` 时工具**本身阻塞**，
> 所以主会话没有"空窗"要填 —— 该做的独立工作应放在**第 4 步扇出之前**做完。
> 只有用异步 `true` 时才需要"边跑边干"。

### ⚠️ 并发数量：有多少派多少，上限 5

**区分两个数字，别搞混**：

| | 数字 | 含义 |
|---|---|---|
| **下限** | **= 可认领任务数** | **有几个可认领就派几个**（这是命令） |
| **上限** | **5** | 超过 5 会**收益递减甚至变差**（这是实证） |

**为什么上限是 5** —— 加 agent 的收益会**先升后降**：

| 并发数 | 效果 |
|---|---|
| 1 | 基准（**退化成单 agent**） |
| **3-5** | **峰值区间** |
| 15 | 产出质量**下降 23%**（相比 5 个时），即使算力翻三倍 |

**两个独立来源指向同一量级**：

- 实测：productivity peaks between **three and five** agents; at 15 agents, **23% decline** in output quality.
- 业界观察：coding swarms **stall at single-digit concurrency**.

**为什么会降**：为避免互相覆盖，任务边界被迫**变粗**（细粒度的活更容易冲突）。
边界越粗 → 可并行的活越少 → 收益被吃掉。这就是 **Brooks 定律**（《人月神话》1975）在 agent 上的复现。

**另一条关键数据**：单 agent 在 **~64%** 的评测任务上**持平或优于**多 agent 管道。
所以**多 agent 不是默认更优** —— 但它也**绝不能退化成"一次派一个"**：
那等于付了多 agent 的冷启动成本，却只拿到单 agent 的并行度，**是最差的组合**。

**因此**：

- **有 N 个可认领任务 → 同一轮派 N 个**（N 封顶 5）
- **只派 1 个是合法的，仅当队列里确实只剩 1 个可认领任务**
- **超过 5 个是红灯**，先回头把任务切得更独立，而不是继续加人
- 加人之前先问：**这些活真的互不依赖吗？** 不独立 → 加了只会更慢

**评审要派给谁**：评审必须是**另一个**子代理（干净上下文），
不要主会话自检——那等于自己给自己签字。

## 任务状态

```text
Inbox → Assigned → In Progress → Review → Done | Failed
```

**规则**：
- **Orchestrator owns state transitions** —— 不要指望 agent 更新自己的状态
- 每次状态迁移记一条 comment（谁、做了什么、为什么）
- Failed 是合法终态——记录原因，继续走

## 任务队列与认领

> **来源**：本节的机制嫁接自 [gak4u/kanban-agent](https://github.com/gak4u/kanban-agent)
> 的 work-item queue convention（MIT），并按其 DSH 约束改造。
> 核心思想：**状态由位置表示，认领必须原子，编号即优先级。**

### 为什么需要队列（第一作用：派发前冲突检查）

**队列存在的首要理由是「在派发前发现文件冲突」**，不是"防止改 plan.md 冲突"。

```text
plan 第 7 步要求每条任务写「预计改动文件/位置」（到函数级）
      ↓
plan 第 9 步把它拆成一文件一任务，放进 tasks/queue/
      ↓
build 派发前：把所有任务的「预计改动文件/位置」拉出来两两比对
      ↓
有交集 → 合并 / 串行 / 划定边界     ← 冲突在这里被挡住
```

**没有队列的后果（实证）**：三个任务（P1 / P2a / P2b）都改
`cmd/server/multiprovider.go`，因为没有队列文件、看不到「预计改动文件」这一栏，
三个子代理被同时派出 → 互相被对方的半成品绊住 → `go build ./...` 间歇性红 →
其中一个报告"另一个 agent 正在并发编辑，我全程未触碰"。
**有一条队列，这三栏写着同一个文件，一眼可见。**

### 派发前的冲突检查（必做）

**每个任务派发前，把本轮要派的 N 个任务的「预计改动文件/位置」列出来比对：**

| 交集情形 | 处理 |
|---|---|
| 同一文件 + **同一函数** | **合并成一个任务** —— 拆开必冲突 |
| 同一文件 + **不同函数** | 可并行，但委派提示词写明"只改 `X()`，不碰 `Y()`" |
| 不同文件 | 直接并行 |

> ⚠️ **字段为空 = 先补上再派。** 没有「预计改动文件/位置」就无法做这个检查，
> 等于把冲突推迟到运行时。

### 第二作用：认领（防重复劳动）

**多 agent 并行的前置条件，是"谁在做哪件事"有记录。**

```text
没有认领记录时的典型事故：
  agent A 读到：Task 3 = 待做
  agent B 读到：Task 3 = 待做     ← 同一瞬间
  两边都开工 → 重复劳动 + 产出冲突 → 白烧两倍算力
```

状态由**目录位置**表示（`pending/` → `claimed/`），认领由 Orchestrator 用 `git mv` 完成 ——
见下方「认领规则」。

### 队列可在执行中追加

**审计 / 排查 / code review 发现的新任务，不需要重开 `plan`** ——
由 Orchestrator 分配下一个 `NNN` 并写入 `pending/` 即可。**队列是活的。**

例：派审计 → 审计发现 4 处漏网（P0/P1/P2a/P2b）→
**直接追加 4 条进 `pending/`**，而不是停下来重做规划。

追加后的任务同样走冲突扫描与依赖检查。

### ★ 孤儿任务恢复（进程崩溃 / 会话中断后必做）

**问题**：任务被 `git mv` 到 `claimed/` 后，如果**进程崩溃、会话中断、
或子代理被 `interrupt_agent` 停掉**，那个任务就卡在 `claimed/` 里 ——
**认领者已经死了，但队列不知道**。它是"孤儿"。

后果：`claimed/` 里堆着永远不完成的项，
`pending/` 看起来是空的 → 误判"全部完成" → goal 提前 `complete`。

#### 启动时 / 每轮开始时的检查

```text
扫 tasks/queue/claimed/ 里的每一项：
  ① 它的「认领者」字段有值吗？
  ② 那个 agent 还活着吗？（list_agents 查 id 是否仍在）

  ├─ agent 仍在   → 正常，继续等（不要动它）
  ├─ agent 不在了 → **孤儿** → 按下方处置
  └─ 字段为空     → 异常（认领没写全）→ 视为孤儿
```

#### 孤儿处置

| 情况 | 处置 |
|---|---|
| 产物**已完整**（验收标准能满足） | 直接移入 `review/` 或 `done/`（按是否需要评审） |
| 产物**半成品**（编译红 / 测试挂） | `git mv` 回 `pending/`，**记录上次失败原因** |
| 工作区被半成品污染 | 先 `checkout` 或回退到基线，再放回 `pending/` |

> ⚠️ **回 `pending/` 时必须带上"上次为什么没做完"** ——
> 否则下次派发会原样重试，撞同一个坑（违反 epoch 循环的"不原样重试"）。

#### 为什么这条必须有

**没有它，"崩溃"会伪装成"完成"。** 这是最危险的一类静默失败 ——
`pending/` 空 + `claimed/` 有孤儿 → 看起来像在等 → 实际永远等不到。

> **判据**：`claimed/` 非空，**但没有任何活着的子代理** → 一定是孤儿，立刻处置。

### 状态：用位置表示，不要用字段

**这是踩过坑的结论**：状态如果写成任务里的一个字段，**它会过期**。

```text
❌ 在 tasks/plan.md 的 Task 3 里写 **状态**：待认领
   → agent 改了字段但忘了同步别处 → 字段与事实不符
   → 而且多个 agent 同改一个 plan.md 会冲突

✅ 状态 = 任务所在的目录
   → 移动是原子的，位置永远是真的
```

**目录布局**（在 `tasks/` 下）：

```text
tasks/
  plan.md                  ← 索引 + 架构决策（人读的总览）
  queue/
    pending/    NNN-slug.md   ← 可认领
    claimed/    NNN-slug.md   ← 已分配（认领者写在文件里）
    review/     NNN-slug.md   ← 已实现，等独立评审
    blocked/    NNN-slug.md   ← 卡住，附「## Blocked」说明
    done/       NNN-slug.md   ← 完成 + 已验证
```

### 认领规则（DSH 改造版）

> ⚠️ **与 kanban-agent 的关键差异**：它是**去中心抢占**（worker 自己 `git mv`），
> 而 DSH 里**子代理不碰 git**（见「Git 归属」）。所以此处是**中心化分配**：
> **只有 Orchestrator 移动任务文件。**

完整分配步骤见下方「依赖处理」第 5 节（含依赖闸门）。
核心是：**取编号最小且依赖已满足的项 → `git mv` → 填认领者 → 派 Builder**。

**为什么仍用 `git mv`**：即使由中心分配，move 仍是原子的 ——
**防止主会话自己并发起两个相同任务**（比如 goal 唤醒与用户输入同时触发）。

### 编号即 FIFO

`NNN` 全局分配一次（`max(existing) + 1`，零填充三位）。
**总是认领编号最小的** —— 不需要额外排序逻辑，优先级编码在文件名里。

### 依赖处理（A 完成后 B 才能做）

**这是"一次性派发"和"依赖"的接合处，也是最容易出问题的地方。**

#### 1. 两种依赖，语义不同

frontmatter 里写：

```yaml
depends_on: 003      # 只要 003 完成即可（顺序要求）
stacks_on: 005       # 需要 005 的**产出内容**（叠在它之上）
```

| 字段 | 含义 | 能否与对方并行 |
|---|---|---|
| `depends_on` | 顺序要求 —— 等 003 **做完** | ❌ 不能（要等 done） |
| `stacks_on` | 内容要求 —— 要在 005 的**产物上**继续 | ❌ 不能（要读它的产出） |

**两者都挡派发，但 `stacks_on` 更严格**：它不仅要对方 done，还要**读对方的具体产出**
（接口、文件、commit）。所以 `stacks_on` 的任务**必须在委派提示词里带上上游的产物路径**。

#### 2. 判定「可认领」

```text
任务 T 可认领 ⟺
  ① T 在 tasks/queue/pending/ 里
  ② T.depends_on 里的每个编号，都在 done/ 里
  ③ T.stacks_on  里的每个编号，也都在 done/ 里
```

**只有满足全部三条，T 才算进"N"**（可认领数）。

#### 3. ★ 解锁即补派（关键规则）

依赖任务最容易被压成串行，就是因为**解锁的时机没处理好**：

```text
❌ 错误：每轮只算一次可认领集
   第 1 轮：可认领 = {001, 003}  → 派 2 个
   001 完成 → 002 解锁，但本轮已结束 → 等下一轮
   第 2 轮：可认领 = {002, 004}  → 再派 2 个
   → 白白多花一轮

✅ 正确：任务完成即重算、即补派
   第 1 轮：派 {001, 003}
   001 完成 → 立刻重算 → 002 解锁 → **本轮马上补派 002**
   003 完成 → 立刻重算 → 005 若解锁 → 继续补派
   → 直到「可认领为空」或「已达上限 5」
```

**规则**：

```text
每有一个任务标为 done：
  1. 重算可认领集
  2. 有新解锁的，且当前在跑数 < 5  → 立刻补派
  3. 重复直到 无可认领 或 在跑数 = 5
```

#### 4. 线性依赖链：并行度会被压成 1

如果依赖是纯线性的：

```text
001 → 002 → 003 → 004 → 005
```

那么**任何时刻只有 1 个可认领**，"本轮只派 1 个"在这里是**合规的**，
但结果是**完全没有并行** —— 5 轮，每轮 1 个。

**这不是派发规则的问题，是任务切分的问题。** 遇到这种情况应该：

| 做法 | 效果 |
|---|---|
| **把链上的任务切宽** —— 如 002 拆成 002a/002b/002c（各自独立） | 恢复并行 |
| 接受串行，但确认它真的是必需的 | 有时确实无法并行 |
| 检查 `depends_on` 是否写得太保守 | 常见错误：明明不依赖却写了依赖 |

> ⚠️ **不要为了让"本轮派多个"达标而强行并行有依赖的任务。**
> 依赖是真实约束时，串行是正确行为 —— 该改的是任务切分，不是绕过依赖。

#### 5. 分配前的检查（每次都要做）

```text
Orchestrator 分配一个任务：
  1. 取 tasks/queue/pending/ 里 编号最小 的**依赖已满足**项
  2. 复核 depends_on / stacks_on 是否都已在 done/     ← 闸门
  3. git mv queue/pending/NNN-x.md queue/claimed/NNN-x.md
  4. 在文件里填「认领者」字段（agent id）
  5. 派 Builder：提示词里带任务文件路径，
     若 stacks_on 有值，**一并带上上游产物路径**
```

**第 2 步不能省** —— 否则会派出一个地基还没打的活。

### 任务文件格式

```markdown
---
id: 007
title: 修复登录重定向循环
type: bug
priority: P1
depends_on: 003
claimed_by:            # Orchestrator 分配时填写
---

## Summary
1-3 句：要什么、为什么。

## Scope
- 范围内：确切的改动
- 范围外：明确排除，防止漂移

## 验收标准（二元、可测）
- [ ] 每条都能客观判定 pass/fail
- [ ] `<仓库的真实测试命令>` 通过

## Result（Builder 填）
- commit：
- 改了什么：
- 验证输出：

## Blocked              ← 仅 blocked 项有此段
卡在哪 / 需要什么输入。
```

### 三条硬规则

**① Builder 不许改 Scope 和验收标准。**

> 如果任务有歧义、自相矛盾、或前提就是错的 → **移到 `blocked/` 附说明，然后取下一个任务**。

这条直防"agent 自己降低标准交差" —— 它只能**如实报告卡住**，不能偷偷把标准改低。

**② 完成 = 已验证（含非功能项）。**

移进 `done/` 之前必须：勾掉每一条验收标准、填完 `## Result`（commit / 改了什么 / 验证输出）、
清理自己造的测试数据。

**并且必须过一遍非功能门禁** —— 按任务特征挂载，不是无条件全读：

| 任务特征 | 必须过的清单 |
|---|---|
| **任何**任务 | `../_shared/references/definition-of-done.md` |
| 触及认证 / 输入 / 数据出口 | `../_shared/references/security-checklist.md` |
| 有性能指标要求 | `../_shared/references/performance-checklist.md` |
| 需要日志 / 指标 / 追踪 | `../_shared/references/observability-checklist.md` |
| 碰前端 UI | `../_shared/references/accessibility-checklist.md` |

> ⚠️ **"功能对了"不等于"能上生产"。** 验收标准回答"做的是不是这个东西"，
> 这些清单回答"**它够不够格进主干**"。
> **命中特征却不跑对应清单 = 未完成**，不许进 `done/`。
>
> 若某项确实不适用，**在 `## Result` 里写明"不适用 + 理由"**，而不是默默跳过。

**③ 只 Orchestrator 碰目录。**

Builder 交付产物 + 在回复里报告状态，**不移动任务文件**（同「Git 归属」的理由）。

### 与 goal 的配合

每轮开始时 Orchestrator **读一眼 `tasks/queue/`**：

| 看到 | 说明什么 | 动作 |
|---|---|---|
| `pending/` 空 + `claimed/` 空 | 全部完成 | → `update_goal complete`（**先确认验证已过**） |
| `pending/` 空 + `claimed/` 非空 + **有活着的子代理** | 在等 | **join，不要开新活** |
| `pending/` 空 + `claimed/` 非空 + **无活着的子代理** | ⚠️ **孤儿！** | **立刻按「孤儿任务恢复」处置** —— 不是"在等" |
| `pending/` 非空 + 无运行中子代理 | 该派发了 | 走派发流程（含孤儿检查与冲突扫描） |

> ⚠️ **中间两行的区别是本表的关键。** `claimed/` 非空**不等于**在等 ——
> 如果没有任何 agent 活着，那是**崩溃留下的孤儿**。
> **把它误判成"在等"，就会永远等下去，或者提前判定完成。**
> 判别方法：`list_agents` 查 `claimed/` 里记录的认领者 id 是否还在。

**这直接解决"挂 goal 空转"** —— 空转的定义就是：
**没有可认领的任务，却仍在开新一轮。** 有了队列，每轮第一件事就是查它。

## 交接（Handoff）

工作在两个 agent 间传递时，交接消息必须含五要素：

1. **What was done** —— 改动/输出摘要
2. **Where artifacts are** —— 精确文件路径
3. **How to verify** —— 测试命令或验收标准
4. **Known issues** —— 未完成或有风险的部分
5. **What's next** —— 接收方的下一个明确动作

反例：*"Done, check the files."*
正例：*"Built auth module at `/shared/artifacts/auth/`. Run `npm test auth` to verify. Known issue: rate limiting not implemented yet. Next: reviewer checks error handling edge cases."*

## 评审门禁

跨角色评审防止质量漂移：

- **Builders review specs** —— "这可行吗？缺什么？"
- **Reviewers check builds** —— "符合规格吗？边界情况呢？"
- **Orchestrator reviews priorities** —— "现在做的是对的事吗？"

**跳过评审，质量会在 3-5 个任务内退化。每次都是。**

### 哪些任务必须评审（触发条件）

**不是每个任务都要评审** —— 那样会拖慢流水线。命中任一条就**必须**派 Reviewer：

| 触发条件 | 为什么 |
|---|---|
| 改动**不可逆**（数据迁移、公开 API、删数据） | 出错代价高 |
| 触及**安全/认证/权限** | 漏掉就是漏洞 |
| 新增或修改**模块边界/接口** | 影响面广 |
| `plan` 里标了**需要独立评审**的任务 | 拆任务时已判定 |
| Builder **报告了不确定**或"已知问题" | 它自己都没把握 |

**其余任务可跳过评审**（但要在队列里记录"未评审"，不隐瞒）。

### 怎么评审

**必须派另一个子代理**（干净上下文）—— 不要主会话自检，那等于自己给自己签字。

```text
任务：评审 <任务文件路径> 的产出
读：<产物路径> + <任务文件的验收标准>
做：逐条核对验收标准，找反例与边界情况
返回：通过 / 不通过 + 具体问题清单 + 复现步骤
约束：⛔ 不改代码，只评判；⛔ 不碰 git
```

### 评审不通过怎么办

```text
Reviewer 报「不通过」：
  1. 任务从 review/ 回退到 pending/（记录驳回理由）
  2. 重新派 Builder —— **带上 Reviewer 的具体问题**，换思路修
  3. 修完再评审
  4. 同一任务连续 3 轮评审不通过 → 移入 blocked/，如实上报
```

> ⚠️ **队列状态与评审的对应**：任务进 `review/` 是因为它**等评审**，
> 不代表完成。只有评审通过（或按上表判定无需评审）才进 `done/`。

## Goal 自挂 + 轮内收束（DSH 默认运行形态）

**只要任务满足"多轮 + 委派"，就按这条走** —— 用本技能时**自动挂 goal** 是预期行为。

> **判定标准的单一来源**：`plan/SKILL.md` 第 11 步（何时建）
> 与 `SKILL.md` 第三步（查 / 复用 / 结束）。
> **本节不重复判定表**，只讲 goal 与轮内收束的配合。

### 1. 判定与收尾 → 见 `SKILL.md` 第三步

- **何时建**：任务队列 ≥2 或需跨轮 → 建；单轮能收束 → 不建
- **何时结束**：队列清空且验收已验 → `update_goal complete`；
  同一阻塞连续 ≥3 轮 → `update_goal blocked`
- 挂了 goal 之后**不要**再向用户确认"要不要继续"，直接推进

### 2. 铁律：一轮之内必须把子代理 join 干净

**这是解决「goal 不能等待」的唯一结构性答案。**

轮次边界只在"这一轮的工具调用全部结束、模型输出最终文本"时出现。
所以只要**在轮内把子代理收回来**，goal 就没有缝可钻：

```text
主窗口一轮的标准骨架：
  0. 先干自己的活    扇出之前，把主会话那份独立工作做完
                     （读文件 / 起草骨架 / 建目录 / 查依赖 / 备验证脚本）
                     ★ 必须在扇出之前 —— 见下方说明
  1. todo_write      写清本轮边界与验收标准
  2. 扇出            默认 subagent(run_in_background: false) × N
                     同一轮发多个 = 真并行，且全部返回后才继续
                     （需脚本化编排/大批量汇总时才用 workflow）
  3. 收敛            默认(false) → 工具返回即已收敛，无需额外动作
                     用了异步(true) → 无事后等待接口，只能等推送（下一轮）
  4. 补派            每个任务 done 后立刻重算可认领集，新解锁的马上补派
  5. 消费 + 交棒      写文件、更新队列与 goal 状态、决定下一轮
```

> ⚠️ **「先干自己的活」必须在扇出之前，不能放在中间。**
> 用默认的 `run_in_background: false` 时工具**本身阻塞** ——
> 一旦扇出，主会话就**没有任何"空窗"可填**。
> （旧版写"扇出后填空窗"只在异步 `true` 时成立，已删除以免误导。）

> ⚠️ **实测校正（两条）**：
>
> **① `subagent(run_in_background: false)` 本身就是阻塞 + 并行。**
> 实测同一轮发 2 个、每个内部 sleep 20 秒：两者 start 相差 0.64s、
> end 相差 0.65s，**总耗时 20s 而非 40s** —— 真并行，且全部完成才返回。
> 所以**默认就该用它**，不需要 `workflow` 来"实现并行"。
>
> **② `job_output` 不能用于子代理。**
> 实测 `job_output(<subagent-id>, wait: true)` 返回 `Error: unknown job` ——
> 子代理 id 与 job id 是两套命名空间。
> **异步子代理没有事后等待接口**，完成时由 runtime 推通知。
> **不要写"用 job_output 等子代理"——那条路不存在。**

**第 3 步的定位**：它是为**异步模式**准备的（`run_in_background: true`）。
如果用默认的 `false`，工具本身阻塞，主窗口没有"空窗"要填 ——
此时把独立工作**放到扇出之前**做，才是正确顺序。

### 3. 按场景选形态（实测校正版）

| 场景 | 用什么 | 能否本轮拿到结果 |
|---|---|---|
| **并行 + 要结果**（绝大多数） | **`subagent(run_in_background: false)` × N** | ✅ **能**（工具返回即全部完成） |
| 大批量（>5）+ 脚本化/结构化汇总 | `workflow(...)` | ✅ 能（前台阻塞） |
| 不需要本轮结果 | `subagent(run_in_background: true)` | ❌ 靠推送通知到下一轮 |
| 本轮本质就是"等结果" | `create_goal(..., max_goal_rounds=1)` | 直接取消续跑语义 |

```text
要并行 + 本轮要结果   →  run_in_background: false × N   ← 默认首选
大批量 + 要脚本编排    →  workflow
不要本轮结果          →  run_in_background: true（结果下一轮到）
```

**关键**：`workflow` **不是**唯一的并行手段，只是"需要脚本化编排"时的选择。
单纯要并行拿结果，**同一轮发多个 `false` 就够了**。

### 4. 写权唯一：等待期间的行为边界

| 子代理在做什么 | 可以 | **不可以** |
|---|---|---|
| 核实代码 | 读代码、写文档、规划、起草 | **改它要核实的代码** |
| 核实某个端口/实例 | 用**别的端口**起独立实例 | **重启/改它正在用的那个** |

**违反的代价**：子代理的结论会与代码状态对不上（它测的是改前，你报的是改后）。
"这次刚好没影响" 不算纪律 —— 那是运气。

### 5. 自检（每轮收尾前）

- [ ] 本轮扇出的每个子代理，都拿到结果或显式处置了吗？
- [ ] 我在子代理跑的时候，有没有碰它正在核实的东西？
- [ ] 本轮最终文本之前，有没有"等通知"这种未兑现的意图？
      （有 → 说明该 join 而没 join，回去 join）
- [ ] 跨轮状态写进文件了吗？

### 6. 别无限等

子代理跑过 ~5-6 轮无产出就该处置：

1. `interrupt_agent <id>` 停掉它
2. **自己跑一遍可独立执行的验证脚本**收尾
3. 如实记录「独立复核未回，以下为自查证据」→ 再判断目标是否达成

## 常见陷阱

- **派发时没写清产物路径** —— 工作产出了却找不到。永远在委派提示词里给出精确输出路径
- **没有评审步骤 = 质量漂移** —— "小改动，跳过评审"，做三次你就会累积错误
- **agent 不报进度** —— 沉默造成协调盲区。要求它 start / blocker / handoff / completion 四个节点都报
- **没确认能力就派活** —— 给没有浏览器权限的 agent 派浏览器测试
- **Orchestrator 亲自干活** —— 你一开始"顺手快点做掉这一件"，就失去了对其余部分的监督视野
- **等待时空烧轮次** —— 见上面「Goal 自挂 + 轮内收束」

## 委派提示词模板

子智能体**看不到父会话**，提示词必须自包含。**但两种类型的要求完全不同**：

| | **讨论型** | **执行型** |
|---|---|---|
| 提示词长度 | **3-5 句** | 自包含（含纪律） |
| 要不要读文件 | ❌ **不要** —— 读了就慢 | ✅ 要 |
| 耗时 | **秒级** | 分钟级 |
| 复用 | ❌ 一次性 | ❌ 一次性（一任务一 agent） |

### 讨论型模板（轻 —— 有疑问时用）

```text
背景：<3-5 句话，只讲必要上下文>
我的疑问：<具体问题>
约束：<关键限制>
请给：你的判断 + 理由 + 风险
⛔ 不要写代码、不要读文件、不要跑命令，**只回答**
```

> ⚠️ **讨论必须快。** "不让它读文件"是"快"的前提 ——
> 一旦要求它去读代码/查资料，就变成分钟级了。

### 执行型模板（给 Builder 用 —— 一次性，一任务一 agent）

```text
任务：<一句话目标>
任务文件：tasks/queue/claimed/<NNN-slug>.md  ← 先读它，Scope 与验收标准以它为准
产物路径：<精确路径>
完成标准：<可验证的命令/信号>

执行纪律（相对 build 技能目录）：
0. ⛔ 不要执行任何 git 命令（add / commit / reset / checkout 都不许），
   也不要移动 tasks/queue/ 下的文件。这些由 Orchestrator 独占。
   你只写文件、跑测试、报告结果。
1. 读 epoch-loop.md —— 原子改进 → **跑 L1**（编译 + 相关测试）→ 报告结果。
   不要跑全量测试（那是 L2，由 Orchestrator 在子问题边界做）。
2. 读 incremental-implementation.md —— 按薄垂直切片实现。
3. TDD 分级（见 SKILL.md）：核心逻辑/修 bug 必须先写失败测试；
   机械改动（配置/文案/重命名）**不必**写测试，但仍要过 L1。

⛔ 不许修改任务文件里的 Scope 或验收标准。
   如果任务有歧义、自相矛盾、或前提是错的 —— 停下来如实报告，
   不要自己把标准改低来"完成"它。
⛔ 只做这一件事。**不要顺手改别处、不要写文档、不要重构无关代码。**

交付时必须给出：
  - 改了哪些文件（精确路径）
  - 怎么验证的（真实命令 + 真实输出摘要）
  - 已知问题 / 未完成部分
  - 是否发生过失败与重试（如实，不隐瞒）
```

> ⚠️ **底线是"把代码写出来、能跑"** —— 除此之外的事**尽量少做**。
> 不写文档、不做无关重构、不顺手优化。**写多了反而制造冲突面。**
>
> 注意第 0 条用的是「报告本轮改动」而不是「commit 本轮改动」——
> 子代理没有 commit 权限，它只负责把改动**落盘**并**说清楚**。

## DSH 等待语义速查（实测校正）

| 工具 | 是否阻塞当前轮 | 能否本轮拿到结果 | 适用 |
|---|---|---|---|
| **`subagent(run_in_background: false)`** | ✅ **阻塞** —— 不返回直到跑完 | ✅ **能** | **默认首选**；同一轮发多个 = 真并行 |
| `workflow(...)` | ✅ 前台阻塞 —— 脚本跑完才返回 | ✅ 能 | 大批量 + 脚本化/结构化汇总 |
| `subagent(run_in_background: true)` | ❌ 不阻塞，立即返回 id | ❌ **不能**（靠推送通知，下一轮） | 不需要本轮结果时 |
| ~~`job_output(job_id, wait: true)`~~ | ⚠️ 阻塞，但**只对 job id** | — | **实测对子代理无效**（`Error: unknown job`） |
| `send_message(agent_id, ...)` | 不阻塞（仅投递） | — | 中途 steer；也可唤醒 idle 子代理 |
| `interrupt_agent(agent_id)` | 立即返回（请求取消） | — | 超时兜底 |

### 实测记录（本机验证，勿凭推断覆盖）

```text
① 同一轮发 2 个 subagent(run_in_background: false)，各 sleep 20s：
     A start=14:14:07.978 end=14:14:27.995
     B start=14:14:08.620 end=14:14:28.645
   → start 差 0.64s / end 差 0.65s / 总耗时 20s（非 40s）
   → 结论：默认模式天然并行，且全部完成后才返回

② subagent(run_in_background: true) 返回：
     "started subagent 4d5d7a4f-..."
   → 只给 id，无结果；结果随后由 runtime 推通知

③ job_output("cf1c9d11-...", wait:true) 其中 id 来自 subagent：
     Error: unknown job cf1c9d11-...
   → 结论：subagent id ≠ job id，job_output 不能用于子代理
```

**关键区分**：`job_output` 的 id 来自"**启动了后台作业的那个工具**"
（例如 `pwsh(run_in_background: true)`）；而 `subagent` 返回的是 **subagent id**，
**两者不通用**。

> **要并行又要在本轮拿到结果 → 同一轮发多个 `run_in_background: false`。**
> 不要用 `true` 然后再想办法"等" —— 那个"等"不存在。

**没有"跳过本轮"的信号** —— 这正是必须在轮内 join 的原因。

## 与其他技能的分工

| | 本文件 | `myagents-router` |
|---|---|---|
| 层面 | **方法论**：角色 / 生命周期 / 交接协议 / 评审门禁 | **路由**：把一句用户意图分派到 4 个子技能 |
| 形态 | 无状态 playbook，跨项目通用 | 有状态（`.task/<MMDD_slug>/` 4 份文档） |
| 角色数 | 多角色（Orchestrator / Builder / Reviewer / Ops） | 单角色 UserProxy |

**选哪个**：要**设计一支团队或定协作规范** → 用本文件。
要**执行一件已对齐的具体任务** → 走 `myagents-router` → `task-implement`。

> ⚠️ 方法论有意分歧，别互相覆盖：本文件要求「Orchestrator 不亲自干活」（保持监督视野）；
> 而 `task-implement` 要求 UserProxy **亲自处理**强耦合改动（因为它没有团队可指挥）。
> 按当前实际有无团队择一执行。

## 一句话

> **goal 负责"跨轮不忘记"，轮内 join 负责"轮内不空转"。**
> 两者同时用才成立；只挂 goal 不 join，就是轮次空烧的根源。
