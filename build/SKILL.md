# Build（构建阶段 · 路由）

> 对应原版 `/build`。
> 核心理念：**One slice at a time。**

## 这个技能怎么用（先读这里）

本技能是**路由技能**。它不把所有规则堆在一处，而是**按步走**，
需要细节时再读对应的资源文件。资源文件都在**本技能目录下**，用 `read` 按相对路径读取。

> ⚠️ 本技能内嵌的资源文件**没有注册成独立技能**，`skill` 工具加载不到它们。
> 一律用 `read <文件名>` 读取（相对本技能目录）。

**四步走**：

```text
第一步  git 基线          —— 开工前第一件事，无例外
第二步  确认 goal         —— 多轮任务必做
第三步  套上 epoch 循环    —— 所有任务通用
第四步  按类型加载子模块    —— 需要细节时读
```

## ★ 角色：主脑写代码，子代理做轻量任务

**主代理（主脑）= 唯一写代码的人 + 唯一碰 git 的人 + 唯一拍板的人。**

```text
主脑
  ├─ 写代码、改文件、跑测试、跑 git      ← 全部自己做
  └─ 轻量活 → 派子代理（探索 / 讨论 / 评审）→ 主脑用结论、自己拍板
```

| | 主脑 | 子代理 |
|---|---|---|
| 写代码 / 改文件 | ✅ **只有它** | ❌ **绝对不写** |
| 碰 git | ✅ **只有它** | ❌ **绝对不碰** |
| 读文件 / 查资料 | ✅ | ✅ **可以**（这正是它的价值） |
| 跑测试 | ✅ | ❌（只允许只读命令） |
| 拍板 | ✅ **只有它** | ❌ 只给意见，没有否决权 |
| 输出 | 可运行的代码 + commit | **文字**（结论 / 观点 / 问题清单） |

**三类子代理任务**：

| | 探索 | 讨论 | 评审 |
|---|---|---|---|
| 做什么 | 读代码/查资料，带回结论 | 给判断 + 理由 + 风险 | 对已完成代码做对抗评审 |
| 读文件 | ✅ | ❌（读了就慢） | ✅ |
| 耗时 | 分钟级 | **秒级** | 分钟级 |

> ★ **探索是子代理最主要的用途** —— 让子代理去读 20 个文件、只带回 5 行结论，
> 主脑的上下文里就只多了那 5 行。**这是主脑省上下文的关键手段。**

> ⛔ **子代理的三条禁令**：不写代码、不改文件、**不写 git**（只读 git 可以）。
> 违反了就是角色越界 —— 主脑会失去对工作区的唯一写权。
> 完整规则（三类任务、提示词模板、决策权分层）见 `subagent-tasks.md`。

**什么时候派**：要读很多文件才答得上来的问题、有多个都说得通的方案、
拿不准某个行为、或要对已完成代码做评审。
**什么时候不派**：读一个文件就知道、有唯一明显解、或纯品味问题（命名/目录/格式）→ 直接定。

> ⛔ **派之前先做机械检索**：这个答案在仓库里吗（grep）？在文档里吗？
> 已经讨论过了吗（翻 `tasks/plan.md` 的「待决问题」）？
> **三条都排除了才派** —— 拿查得到的东西去问，是把该自己做的事推出去。
> **例外**：要读的文件超过 3 个 → 别自己读，直接派探索子代理（省上下文）。

## 第一步：git 基线（每个任务都做，无例外）

**开工前第一件事永远是确认 git 基线。** 这不是可选项，也不因任务大小而豁免。

```bash
git rev-parse --is-inside-work-tree   # exit 128 = 不是仓库
```

- **不是仓库** → `git init`；目录含大量历史杂物时先写 `.gitignore`
  把追踪范围收窄到交付物路径，再提交基线
- **是仓库** → 确认工作区状态干净（或已提交既有改动），再记下当前 commit 作为基线
- **首次 commit = 本任务的起点 checkpoint**

> ★ **基线是失败回退的唯一安全网。** 没有基线，`reset` 无处可退，
> epoch 循环就退化成「改坏了只能硬修」。所以基线先于一切。

> **谁执行 git**：**写操作只有主脑**。子代理**不执行任何写 git 命令**（只读的
> `log`/`diff`/`status` 可以），也不改任何文件 —— 它们只回文字。
> 所以工作区里**永远只有一个写者**，`git status` 始终可解释，回退点始终可信。
> 完整规则见 `subagent-tasks.md` 的「三条禁令」。

## 第二步：确认 goal（多轮任务必做）

> **判定标准的单一来源**：`../plan/SKILL.md` 第 11 步。
> 本步只做「查 + 沿用」，**不另立标准**。

### 先查，再决定

**`goal` 通常已由 `plan` 建好了**（plan 第 11 步：用户确认后，任务数 ≥2 就建）。
所以这里**第一步是查，不是建**：

```text
get_goal
├─ 已有 goal  → 复用它。确认 objective 含「每轮先读 tasks/plan.md」纪律；缺了就 update_goal 补上
└─ 没有 goal  → 按 plan 的标准判断（任务数 ≥2 / 多轮 / 需跨轮）→ 该建就建
```

**判定标准（与 plan 一致，不要另立）**：

| 条件 | 动作 |
|---|---|
| 任务清单 ≥2 个，或需跨轮推进 | `create_goal(...)` |
| 单轮内能收束 | 不建，直接做完 |
| 用户在等一个即时答案 | 不建 |

**不要问用户** —— 该建就直接建。
**只在主会话建**：`create_goal` 拒绝子代理调用（subagent authority）。

### objective 必须含每轮纪律

**不要把 objective 写成一句话目标。** 它**每轮都重新注入上下文**，
是「按任务定制的常驻提示词」 —— 这是**替代 agent preset** 的办法：

> **完整模板在 `../plan/SKILL.md` 第 11 步（单一来源）—— 不要在这里另写一份。**
>
> 写 objective 时**必须包含两件事**：
>
> 1. **每轮怎么推进** —— 取编号最小的未完成任务，做一个 epoch
>    （原子改进 → L1 廉价验证 → 通过 commit / 失败回退换思路）
> 2. **收尾怎么走** —— 全部任务完成后**必须走交付前门禁四步**
>    （① 全量回归 ② L3 机器判定 ③ 交给人验收 ④ 去 review），**一步都不能跳**
>
> ⚠️ **objective 是每轮重新注入的文本 —— 它漏了哪一步，那一步就会被每轮跳过。**
> 所以门禁必须写进 objective 本身，光写在下面这张收尾表里不够。

### ★ 收尾：goal 必须被显式结束

**建了 goal 就必须结束它 —— 否则它会继续唤醒你，变成新的空转源。**

每轮开始读 `tasks/plan.md` 时，**同时判断 goal 该处于什么状态**：

| 计划状态 | goal 动作 |
|---|---|
| 全部任务完成 + ①② 跑过 + **③ 人验收过 + ④ review 过** | **`update_goal(complete)`** |
| 全部任务完成，但**人还没验收** | ⛔ **保持 active，等人** —— 别提前 complete |
| 还有未完成任务 | 保持，继续下一个 epoch |
| 同一阻塞**连续 ≥3 轮**未解决 | **`update_goal(blocked)`**，写明具体阻塞原因 |
| 需要人决策而无法推进 | **`update_goal(blocked)`**，或暂停等人 |
| **用户叫停 / 改了需求** | **`update_goal(pause)`**，或按新需求 `edit` objective —— 不要留着它空转 |

> ⛔ **`complete` 的判据里「人已验收」是硬条件。**
> ①②④ 都是 agent 自己能判的，**只有 ③ 不是** —— 而它恰恰最容易被跳过：
> 「测试全绿」不等于「功能对」。**在人说 OK 之前，goal 必须留在 active。**

### ★ 交给人的端到端验收（agent 做不到的部分）

**agent 能做的全做完后，必须显式交接给真人。** 这是 agent 的天然盲区：

| 能力 | agent 能吗 |
|---|---|
| 单元 / 集成 / 编译 / 类型检查 | ✅ 能 |
| **端到端体验**（顺不顺、好不好用、像不像样） | ❌ **做不到** |
| **业务判断**（这功能对不对、够不够） | ❌ 做不到 |

**收尾时给出这段（不是让人从零开始测）：**

```text
【交给人验收】
- 做了什么：<一句话>
- 怎么访问：<URL / 命令 / 步骤>
- 我已验证的：<自动化验证结果（测试/构建输出摘要）>
- 我没验证的（需要你）：<端到端体验 / 业务判断 —— 具体说明>
- 请重点看：<3 条以内，可勾选>
```

> ⚠️ **不要因为「测试都绿了」就宣布完成。**
> 测试绿 = **功能按预期工作**；端到端验收 = **这东西对不对、够不够好**。
> **后者只有人能判。** 明确说出「这部分需要你测」，而不是含糊地说「完成了」。

> ⚠️ **`blocked` 不是失败，是如实上报。** 判别标准是「**同一阻塞连续 ≥3 轮**」，
> 不是「这轮不顺利」。难度大、还有活可干，都**不算** blocked。

> ⚠️ **内部决策不是 `blocked` 的理由。**
> **用哪个库 / 什么架构 / 怎么命名 / 目录怎么分 / 用哪个框架** ——
> 这些**一律自己定（必要时派顾问讨论），不许上报人**。
> 详见 `subagent-tasks.md` 的「决策权分层」。
> **只有内部争议 2 轮无共识，才允许升级给人。**
>
> ⚠️ **`complete` 必须真的达成**，不能因为「轮次跑够了」就完成。
> 判据是**验收标准已被真实验证**，与 `plan` 的完成自检一致。

> ⚠️ **「挂 goal」是本技能最容易被漏掉的一步。** 只读到「goal」这几个字
> 而没真正调用 `create_goal`，就等于没有挂 —— 症状是：主会话一直开新轮、
> 每轮都不知道在推进什么，**空烧轮次**。
> **看到「goal」这个词不等于建了 goal，必须真的调用工具或确认已存在。**

## 第三步：套上 epoch 循环

**所有任务都套这层循环。** 读 `epoch-loop.md`：

```text
基线 commit（第一步已建）
for 子问题 in 分解出的序列:
    基线 = 当前 commit（该子问题的 checkpoint）      ← 子问题级粒度
    for epoch in 1..N:
        1. 原子改进（一次只推一个点）
        2. 验证：**只跑 L1 廉价信号**（编译 + 相关测试，秒级）
           不要每轮跑全量测试/构建
        3. 通过 → commit（新基线）                  ← 轮次级粒度
           失败 → git reset --hard 回基线
                  + 记录失败原因 + 换思路（不原样重试）★
    子问题达成 → 跑 **L2**（受影响包 ∪ 反向依赖包）→ commit 固化，成为下一子问题的新基线
```

> ★ **注意层级 —— 这里的「子问题」就是 `tasks/plan.md` 里的一个任务（T1/T2…）。**
> **一个任务内部跑 N 个 epoch**（每个 epoch = 一个原子改进 + 一次 commit）。
> 所以「完成一个任务」= 它内部的 epoch 循环收敛了 + 跑过 L2 + 勾选 + commit，
> **不等于「只改了一次」**。
> （`plan` 侧同一句话见 `../plan/SKILL.md` 第 9 步。）

> ★ **单写者让回退变简单，但没让回退变免费。**
> 工作区里只有主脑自己的改动，所以 `reset --hard` 不会毁掉别人的成果 ——
> **但有三个坑**（完整三步见 `epoch-loop.md` 第 6 节）：
>
> 1. **`tasks/plan.md` 会被一起回退** —— 它记着勾选和追加的新任务，
>    回退前先单独 commit 把它摘出去，否则下一轮重做已完成的工作**且不报错**
> 2. **`reset --hard` 不删未跟踪文件** —— 本轮新建的文件会留下来污染下一轮
> 3. 优先**定点回退**（`git checkout -- <本轮改动的文件>`），别一上来就 `reset --hard`

> ★ **每完成一个任务，两件事一起做**：在 `tasks/plan.md` 里把那一项**勾上**，然后 commit。
> 勾选是「下一轮该做哪个」的唯一依据（`build` 取**编号最小的未勾选任务**：
> 匹配 `- [ ] **T<n>**` 这种行 —— **Checkpoint、待决问题、完成自检的勾选框不算任务**）——
> **只在脑内记住「做完了」，跨轮或上下文压缩之后就不存在了。**
> 中途发现的新任务同样追加进清单（下一个编号），不要只留在对话里。

**三级验证 + 一道交付门禁**（详见 `epoch-loop.md`）：

| 级别 | 何时 | 跑什么 |
|---|---|---|
| **L1** | **每个 epoch** | 编译 / 类型检查 + **只跑与本次改动相关**的测试（秒级） |
| **L2** | **每个子问题完成** | **受影响包 + 反向依赖包**的测试 + 构建（见下，别跑全量） |
| **L3** | **交付前** | 非功能清单 —— **机器判定型保留，静态阅读型交给 `review`**（见下） |
| **★ 全量回归** | **交付前（进 `review` 之前）** | **跑一次完整测试套件** —— 见下方「交付前门禁」 |

> ⚠️ **验证粒度要匹配改动粒度 —— 贵的验证跑最少次。**
> 每轮都跑全量 = 改一个变量也等 4 分钟。
>
> ⛔ **不许重复验证未变的代码** —— 这轮没改到 X，就不要重跑 X 的测试。

### ★ 交付前门禁（进 `review` 之前，四步都要过）

**这是 build 的出口 —— 走完才算「实现完成」。**
缺任何一步，后面都等于在验收一个不完整的产物。

```text
① 全量回归      跑一次完整测试套件（不是 L2 的缩小集）
② L3 机器判定   密钥扫描 / 依赖供应链 / 性能基线 / 可观测契约（自动化命令）
③ 交给人验收    端到端体验 + 业务判断（见第二步「交给人的端到端验收」）
④ 去 review     合并前的质量门禁 —— 那是 `review` 技能的职责
```

> ⛔ **① 不能省。** L2 只覆盖「**我算出来的那些包**」——
> **反查算错不会报错，只会静默少测**（依赖靠字符串/反射/DI 容器建立、
> monorepo 的路径别名解析不到、测试夹具包的引用方向反了 —— 静态图都看不见）。
> 全量回归是唯一的兜底。
> **这是 L2 缩小规则的对价：敢缩小，就得留一道全量门。**

> ⚠️ **别在仓库里没有测试套件时假装走完 ①。** 没有测试可跑，
> 就如实说明「本仓库无自动化测试，① 不适用」，并把验证重心压到 ③ 交给人。
> **把「没跑」写成「跑过了」是本工作流最严重的错误。**

### ★ L2 只跑「受影响包 + 反向依赖包」

**这是本工作流最有效的一条提速规则** —— 减少绝对工作量，且不引入任何新机制。

```text
git diff --name-only → 映射到包 → 反查哪些包依赖它
L2 测试集 = 受影响包 ∪ 反向依赖包
```

**例**：改 `internal/auth/token.go` → 跑 `internal/auth` + 所有 import 它的包。

**敢缩小的前提是三个安全条件同时满足**（完整推理见 `epoch-loop.md` 的「L2 怎么跑」）：

| # | 条件 | 一句话 |
|---|---|---|
| ① | **依赖图现算** | 用缓存的索引，反查结果可能是**上一版**的，而且不会告诉你 |
| ② | **改语义/契约时强制全量** | 反向依赖图只覆盖静态 import；改「默认值 / 输出格式 / 协议」时它看不见下游的隐式约定 |
| ③ | **保留全量逃生口** | 交付前跑一次全量回归（见上方「交付前门禁」） |

> ⚠️ **算错不报错，只静默少测。** L2 绿了只代表「**我算出来的那些包**没问题」。
> 所以 ③ 不能省 —— 它是整条缩小规则的对价。

### ★ L3：机器判定型 / 静态阅读型分流

L3 的清单有**两类**，处理方式不同：

| 类型 | 例子 | 归属 |
|---|---|---|
| **静态阅读型**（读 diff 就能判） | 「这段有没有 SQL 拼接」「有没有 N+1」 | **交给 `review`** —— 它五轴已含 security/performance，且同样看 diff |
| **机器判定型**（要工具/仓库级/运行时） | 依赖供应链、**密钥扫描**、**性能基线实测**、可观测契约 | **保留在 L3**，改成自动化命令 |

**为什么机器判定型不能下沉**：

- **供应链**：要读 lockfile 与**基线对比** —— 仓库级状态，不是 diff 文本
- **密钥扫描**：要扫**全历史** + 熵/正则判定
- **性能基线**：「这次是否让 P95 退化」必须**实测**，review 只能预测
- **可观测契约**：指标名**全局唯一性**要跨模块查重

> ⚠️ **还有两类 `review` 结构上够不到的**，所以 L3 不能整段删：
> - **累积退化**：每次 +15ms 都在噪声内，8 个 diff 后 +120ms，**没有任何单独 diff 可被指责**
> - **可观测性「缺席」**：少一个指标/日志字段 —— **缺席在 diff 里没有文本可审**

**双粒度 checkpoint**：每个子问题一个基线 commit（里程碑级），
子问题内部每轮原子改进也 commit（轮次级）。两者都要有。

> **小任务也要走**：改动小 → 子问题序列只有 1 个，epoch 可能只跑 1 轮，
> 但**基线与 commit 照做**。「这次太小了不用建基线」是明确的红灯 ——
> 恰恰是小改动最容易在乱改中失去可回退点。

> ★ 失败回退分支只在 `epoch-loop.md` 完整展开；
> `incremental-implementation.md` 是切片内的局部循环，两者配合使用。

### TDD 分级：核心逻辑才强制

**不是每个切片都要先写失败测试。** 强制 TDD 在机械改动上性价比极低。

| 改动类型 | 要不要 TDD | 例子 |
|---|---|---|
| **核心逻辑**（分支/计算/状态机/边界） | ✅ **必须** —— 先写失败测试 | 限流算法、金额计算、权限判定 |
| **修 bug** | ✅ **必须** —— 先写复现测试 | 任何 bug fix |
| **接口 / 契约** | ✅ 建议 | 新 API、跨模块边界 |
| **机械改动** | ❌ **不必** | 改配置、改文案、重命名、调格式、搬文件 |
| **纯 UI 样式** | ❌ 不必（但要有手动确认步骤） | 调间距、改颜色 |

> **判据**：**「这段代码写错了，有没有可能不报错、静默算错？」**
> - **有** → **必须 TDD**（静默错误最贵，测试是唯一防线）
> - **没有**（错了会立刻编译失败 / 一眼看见）→ **不必**

> **为什么敢放松**：机械改动**不引入逻辑分支**，不存在「静默算错」。
> 强制给它们写测试 = 把时间花在**不可能出那类错**的地方。
>
> **放松 ≠ 不验证**：机械改动仍要过 **L1**（编译 / 相关测试），
> 只是不要求「先写一个会失败的测试」。

> 这层管「**切片内怎么写**」；第三步的 epoch 循环管「**跨轮怎么推进与回退**」。
> 两层同时生效，不互相替代。

### 什么时候该派对抗评审

主脑写完一段，想验一次「有没有看漏」时 —— 派**评审档**子代理
（它**要读文件**，与秒级的讨论档不同）。详见 `subagent-tasks.md`。

**触发条件**（不要每点改动都派）：不可逆改动 / 安全敏感 / 公开接口 /
主脑自己心里没底。

> ⚠️ **不要把「主脑自检」当成评审。** 想拿独立视角就必须派子代理 ——
> 自己给自己签字等于没签。
> ⚠️ **提示词里只给路径与依据，不要喂自己的结论** —— 否则它只会复述你。

## 边界

**做**：把已规划的任务实现出来，保证每步可运行、可验证、可回退。

**不做**：
- ❌ 不做需求对齐与规划 —— 那是 `define` / `plan` 阶段的职责
- ❌ 不做上线发布 —— 那是 `ship` 的职责
- ❌ 不做合并前评审 —— 那是 `review` 的职责（本技能的 `doubt-driven-development.md`
  是**进行中**的对抗姿势，不是最终裁决，两者不同）
- ❌ **不把代码交给子代理写** —— 子代理只做轻量任务（见 `subagent-tasks.md`）
