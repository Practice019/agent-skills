# Subagent Tasks（子代理只做轻量任务）

## ★ 一句话

**子代理做轻量任务：探索、讨论、评审。代码由主脑自己写。**

轻量 = **只读、只回文字**。子代理的输出永远是一段文字或一份结论报告；
把它变成文件、代码、commit 的**永远只有主脑**。

## ⛔ 三条禁令（硬规则，不得放宽）

| 禁令 | 说明 |
|---|---|
| **不写代码** | 一个字符的实现代码都不产出。示例代码只能写在**回复正文里**当说明 |
| **不改文件** | 不用 `write` / `edit`，不改任何文件 —— 包括 `.md` |
| **不碰 git（写操作）** | **只读 git 可以**（`log`/`diff`/`status`/`show`/`blame`）；**写操作一律禁止**（`add`/`commit`/`reset`/`clean`/`checkout`/`switch`/`branch`/`stash`/`push`）—— 主脑独占全部写 git |

**允许**：读文件、grep、列目录、跑**只读命令**（含只读 git）、查文档、读测试输出。
**不许**：任何有副作用的动作 —— 改文件、装依赖、**写 git**、动数据库、写缓存。

> ⚠️ **「只读命令」的判定看副作用，不看命令名。**
> `git log` 只读没问题；但 `npm test` / `cargo build` / 任何**会写缓存、快照、
> 构建产物**的命令**不算只读** —— 它们会改变工作区，让主脑的 `git status` 变得不可解释。
> 拿不准就问自己：**这条命令跑完，`git status` 会不会多出东西？**

> 违反了就是**角色越界**：主脑失去对工作区的唯一写权，
> `git status` 变得不可解释，回退点失效。

### 主脑的独占权（对应地）

| 动作 | 谁做 |
|---|---|
| 读文件 / 探索代码 | 主脑，**或子代理**（这正是子代理的价值，见下） |
| 写代码 / 改文件 | **只有主脑** |
| `git add` / `commit` / `reset` | **只有主脑** |
| 跑测试 / 跑命令 | 主脑（子代理只跑只读命令） |
| 最终决策 | **只有主脑（拍板）** |

### ★ 为什么值得派子代理去探索（上下文红利）

主脑的上下文是最贵的资源。**让子代理去读 20 个文件、只带回 5 行结论**，
主脑的上下文里就只多了那 5 行 —— 而不是 20 个文件的全文。

```text
❌ 主脑自己读 20 个文件 → 上下文塞满 → 后面写代码时没空间了

✅ 派探索子代理：「查清 X 的调用链，只回：入口函数 + 关键数据结构 + 3 处陷阱」
   → 子代理读 20 个文件（消耗它自己的上下文）
   → 主脑只收到 5 行结论
```

**这是子代理最主要的用途。** 探索、调研、读代码找答案，全都属于这一类。

## 三类子代理任务

| | **探索** | **讨论** | **评审** |
|---|---|---|---|
| 做什么 | 读代码 / 查资料，带回结论 | 给判断 + 理由 + 风险 | 对**已完成的产物**做对抗评审 |
| 审什么 | —— | —— | **代码 / 设计决策 / 断言**都算产物（见 `doubt-driven-development.md`） |
| 读文件 | ✅ 要 | ❌ **不读**（读了就慢） | ✅ 要 |
| 耗时 | 分钟级 | **秒级** | 分钟级 |
| 输出 | 结论报告（**量由 brief 定**，见下） | 3-5 句观点 | 问题清单 |
| 典型问法 | 「X 怎么实现的」「Y 在哪被调用」 | 「A 还是 B」「这个设计有坑吗」 | 「这段有没有看漏」「这个决策站得住吗」 |
| **频率** | 随时（要事实就派） | 随时（秒级，代价低） | **全程一次 —— 交付前** |

> ⚠️ **三类的提示词要求完全不同**，别混用。
> 拿讨论的短提示词去让子代理探索，它读不到东西只能瞎猜；
> 拿探索的提示词去问一个观点问题，纯属浪费分钟级的时间。

> ★ **为什么「评审」降到一次，而「探索」可以随时派** —— 判据是**可替代性**：
>
> | | 探索 | 评审 |
> |---|---|---|
> | 交回什么 | **素材** | **判决** |
> | 主脑自己能拿到吗 | **能** —— 自己读同样文件，只是慢 | **拿不到** —— 结构性盲区 |
> | 换的是 | 时间与上下文（**可替代**） | 正确性（**不可替代**） |
>
> 所以：**探索的频率可以用「贵不贵」压；评审不能压到零，只能压到「一次」** ——
> 它是一道**闸门**，不是一次昂贵的读取。
> 实测支撑：一次评审的 27 条里，至少 2 条是主脑自查不出来的（「改动只做了一半」这类，
> 同作者重读自己的 diff 永远查不出来；测试抓不到，lint 只覆盖可形式化的规则）。

> ⚠️ **「限量」是探索的默认，不是铁律 —— 输出量由 brief 决定。**
> - **事实型探索**（「X 在哪被调用」）→ 限量，≤10 行
> - **设计型探索**（如 `../plan/DESIGN-IT-TWICE.md` 的并行设计方案）→
>   天然要几十行（接口 + 用法 + 取舍），**那是它的产出，不该砍**
>
> **真正不可放宽的是三条禁令**（不写代码 / 不改文件 / 不写 git），
> 以及**只回文字、不落盘**。限量只是为了让事实型探索别倒垃圾。

> ⛔ **不要把「评审」归并进「探索」。** 两者机制相同（读文件、只回文字、限量输出），
> 但**默认倾向相反**：探索要**收敛到结论**，评审要**默认怀疑、产出缺陷清单**；
> 验收口径也不同（探索重精确率，评审重召回率）。
> 归并后评审会滑回「整体没问题，顺便两点」而放过本该拦的问题 ——
> 而且**派发记录里再也分不出「做过评审」和「做过探索」，失效不会报警**。
> 已讨论过一轮：提案方与对抗方**独立得出同一结论 —— 不归并**。

### 探索：提示词模板（事实型 —— 默认）

**关键：限定输出量。** 不限定的话它会把读到的全倒给你，红利就没了。

```text
任务：查清 <具体问题>
范围：<从哪找，可给目录/文件线索>
请只回（≤10 行）：
  · 结论
  · 关键文件:行号
  · 陷阱 / 反直觉的地方
⛔ 不要贴大段源码、不要改任何文件、不要写 git
```

> **设计型探索**（要它产出**方案**而不是答案）用另一套 brief：
> 见 `../plan/DESIGN-IT-TWICE.md` —— 它要求给出接口、用法示例与取舍，
> **输出几十行是正常的，不该砍**。同样只回文字、不落盘。

### 讨论：提示词模板

```text
背景：<3-5 句话，只讲必要上下文>
我的疑问：<具体问题>
约束：<关键限制>
请给：你的判断 + 理由 + 风险
⛔ 不要写代码、不要读文件、不要跑命令、不要改任何文件，**只回答**
```

**提案 + 对抗**的成对写法（重大决策用）：

```text
[提案方]
背景：…
我的方案：…
请给：可行性与风险，3-5 句

[对抗方]
背景：…
有人提议：…
请**只输出问题与反驳**，3-5 句，**不要总结优点**
```

> ⚠️ **必须显式写「不要总结优点」。** 否则对抗方会给你一段
> 「方案不错，但……」的客气话，起不到证伪作用。

### 评审：提示词模板（**交付前一次，别高频派**）

**频率是固定的：全程只跑一次，在交付前门禁 ④ 之前。**
平时（每个 epoch / 每个任务）不派 —— 那些由 L1 / L2 + 自查覆盖。
写完一段就派一次 = 把分钟级往返塞进关键路径，那正是「慢、贵」的来源。

```text
角色：对抗型评审者
要评的文件：<精确路径，可列多个>
评判依据：<验收标准 / 契约 / 需求原文>
请只输出：问题、反例、边界情况、被忽略的约束
⛔ 不要写代码、不要改文件、不要写 git —— **只输出问题，不要总结优点**
```

> ⚠️ **不要把「主脑自检」当成评审。** 想要独立视角就必须派子代理 ——
> 自己给自己签字等于没签。
> ⚠️ **提示词里只给路径与依据，不要喂自己的结论** —— 否则它只会复述你。
> ⚠️ **用的是 `true` 的话，记得对台账** —— `true` 停滞是**静默**的
> （见 `epoch-loop.md` 第 7 节的「派发台账」）。

> ★ **完整方法见 `doubt-driven-development.md`** —— 它给出可**逐字复用**的对抗提示词，
> 以及 CLAIM / EXTRACT / DOUBT / RECONCILE 五步流程和跨模型二次意见的升级路径。

## 什么时候派 / 不派

| 该派 | 不该派 |
|---|---|
| 要读**很多文件**才能回答的问题（探索） | 读一个文件就知道 |
| 有**多个都说得通**的方案，选哪个影响大 | 有唯一明显解 |
| 拿不准某个 API/库/做法的行为 | 查一下文档就知道 |
| 对**已完成代码**的对抗评审 —— **只在交付前派一次** | 纯事实查询（自己 grep） |
| 架构 / 接缝 / 数据流的分叉点 | 品味问题（命名、目录、格式）→ **直接选，走** |

**派几个** —— 先分清是哪一种派发：

| 派发类型 | 要的是 | 派几个 |
|---|---|---|
| **冗余派发** | 同一个问题多份意见，求保险 | **≤2 个**（一个提案 + 一个对抗）；3 个以上收益迅速递减 |
| **多样性派发** | 每个拿**不同约束**，要**不同方案** | **可以 3–4 个**（见 `../plan/DESIGN-IT-TWICE.md`） |
| 日常疑问 | 一个判断 | **1 个** |

> ⚠️ 区别在于**它们是不是被要求给出不同的东西**。
> 都回答同一个问题 → 第 3 个开始就是浪费；各拿不同设计约束 → 第 3 个仍有信息量。

> ⛔ **绝不派子代理去实现。** 想「这个让子代理做掉」的念头本身就是要纠正的信号。
> 子代理只回来文字，**代码永远是主脑自己敲**。

## ⛔ 派之前先做机械检索

```text
准备派子代理之前，先问：
  ① 这个答案在仓库里吗？   → grep / 读文件，自己找
  ② 这个答案在文档里吗？   → 查 README / 类型定义 / 官方文档
  ③ 这个答案已经讨论过了吗？ → 翻本会话 / tasks/plan.md 的「待决问题」
  三条都排除了，才派。
```

> ⚠️ **但「机械检索」的例外正是探索档**：当你判断「要读的文件超过 3 个」时，
> **不要自己读** —— 那会吃掉主脑的上下文。直接派探索子代理。
> 判据不是「能不能查到」，而是「查它要花掉多少上下文」。

## 讨论机制（全程可用，不限阶段）

**这是全程机制，不是某个阶段的步骤。凡有疑问就讨论。**

```text
遇到内部决策
  │
  ├─ 是「品味问题」吗？（命名 / 目录 / 代码风格 / 格式）
  │    └─ 是 → **直接选一个，走。不讨论。**
  │            （这些没有客观对错，讨论纯属浪费时间）
  │
  └─ 不是（影响功能的内部决策）
       └─ 开讨论：
            ① 主脑给方案 + 理由
            ② 子代理给意见（**可以反对，也可以同意**）
            ③ 双方一致 → ✅ 定
               有分歧   → 改方案再议
            ④ 2 轮仍无共识 → 才上报给人
```

**规则要点**：

- **谁提案谁先给理由**，不要只丢一个结论
- 子代理**可以同意也可以反对** —— 不强制它唱反调
- **主脑拍板** —— 子代理的意见是**参考性**的，没有否决权
- **2 轮上限**：两轮还吵不出结果，说明没有明显更优解，**继续吵是浪费**，交给人

> **采纳的判据**：双方**独立**同意 **且** 有实测证据/文档依据 → 采纳。
> 只有一方主张、或依据是「一般人都这么做」→ 不采纳。
> **别因为「子代理说了」就改** —— 那等于把决策权让出去了。

> ⚠️ **也不要只在「想确认自己是对的」时才讨论** —— 那样讨论会退化成走过场，
> 把子代理的同意当背书。**真有多个选项时才讨论。**

> **参考零成本的客观信号**：如果编译/测试**已经跑过**（红了就是红了），
> 顺手看一眼是应该的 —— 这不叫「验证流程」，是不假装看不见已知事实。
> **但不要为了决策专门去写检查** —— 内部决策走讨论。

## 决策权分层（谁定什么）

**核心原则：内部的事主脑自己定；外部的事交给人。**

人的注意力是稀缺资源。**动不动就上报 = 把该自己解决的问题推给人。**

```text
┌──────────────────────────────────────────────┐
│ 内部 —— 主脑（必要时讨论）决定，不用问人          │
│   · 技术栈 / 库选型     · 架构 / 模块划分        │
│   · 实现方式 / 算法     · 目录结构 / 命名        │
│   · 测试框架           · 函数怎么写             │
├──────────────────────────────────────────────┤
│ 外部 —— 交给人                                │
│   · 要什么功能（范围）  · 端到端验收（真人测）    │
│   · 不可逆操作（告知，见下）                     │
└──────────────────────────────────────────────┘
```

### ⛔ 不要问人的情况（这是治「什么都来问」的关键）

> ❌ 用哪个库 / 什么架构 / 变量怎么命名 / 目录怎么分 /
> 用哪个测试框架 / 这个函数怎么写 / 选什么算法
>
> **以上一律自己定，不要上报。**

| ✅ 该问人 | ❌ 不该问人 |
|---|---|
| 功能范围变了 | 用哪个库 |
| 端到端验收 | 什么架构 |
| 不可逆操作确认 | 变量/目录/文件命名 |
| 需要人给权限/资源 | 用哪个测试框架 |
| 业务规则有歧义 | 实现细节怎么写 |

### ★ 不可逆操作：先告知人（不必等回复）

| 操作 | 处理 |
|---|---|
| 数据迁移 / 删数据 / 公开 API 变更 / 改他人负责的代码 | **先告知人**，知会后继续 |

**为什么**：不可逆的错，事后修成本极高。
**告知不是为了征求许可，是为了让人有机会喊停。**

> ⚠️ **卡住（blocked）不是上报内部决策的出口。**
> 内部问题没讨论就宣布卡住 = 把该自己解决的问题推给人。
> 只有**外部问题**（功能范围、端到端验收、权限）或**2 轮无共识的内部争议**才该上报。

## 常见陷阱

| 陷阱 | 症状 | 纠正 |
|---|---|---|
| **派子代理去实现** | 想「这个让子代理做掉」 | ❌ 主脑自己写。子代理只做轻量任务 |
| **探索不限输出量** | 它把读到的全倒回来 | 提示词写死「只回 ≤10 行 + 文件:行号」 |
| **讨论档让它读文件** | 讨论变成分钟级 | 问题描述清楚；要读文件就改派探索档 |
| **对抗方唱赞歌** | 回复全是「方案不错」 | 提示词加「只输出问题，不要总结优点」 |
| **拿子代理当背书** | 「子代理说 A 好，所以用 A」 | 主脑拍板；依据是实测与文档，不是投票 |
| **该探索却自己硬读** | 主脑一口气读 20 个文件 | 超过 3 个文件 → 派探索子代理 |
| **派了不等结果** | 派完就去干别的，却指望本轮用上它 | 要么用 `false` 明确等，要么承认这轮拿不到（`true`）。**别既不等又指望** |
| **以为 `false` 挂住会超时** | 干等着，或以为它会自己退出 | ⛔ **`subagent` 没有声明超时** —— `false` 一停滞就**锁死整轮**。识别签名与恢复步骤见 `epoch-loop.md` 第 7 节 |
| **让子代理去跑测试/改环境** | 「你去验一下」 | ❌ 主脑自己跑。子代理只跑只读命令 |
| **用子代理评审自己刚写的** | 提示词里带了自己的结论 | 只给路径与依据，别喂结论 —— 否则它只会复述你 |

## 与 build 本体的关系

| | 本文件（子代理这一层） | build 本体（实现这一层） |
|---|---|---|
| 回答 | **什么活交给子代理**、意见怎么用 | 代码**怎么**写才对 |
| 你的角色 | 主脑（自己写，自己拍板） | 同一个主脑 |
| 生效范围 | 派子代理前 / 探索与决策走不通时 | 每个 epoch 内部 |

> **关键**：主脑**既**做决策**也**亲手实现 —— **没有**「编排者 / 执行者」的分工。
> 所以也别再按那个框架理解这两份文件：它们是**同一个主脑的两组规则** ——
> 一份管「什么时候找人问」，一份管「代码怎么写」。

## 一句话

**子代理做轻量任务：探索、讨论、评审 —— 全部只读、只回文字。**
代码、文件、git 全归主脑。
该探索的别自己硬读（那是上下文红利），该拍板的别推给人（那叫决策）。
